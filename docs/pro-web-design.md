# EnvHandoff Pro 웹 설계 초안

작성일: 2026-09-24. 이 문서는 Pro를 웹에서 먼저 제공하고, 설치형 앱은 필요한 경우 같은 API를 쓰도록 추가하는 방향의 초안이다. 기존 [제품 계획](product-plan.md)의 v3.0·v4.0 기능과 보안 조건을 바꾸지 않는다. 배포 경로의 근거는 [조사 결과](pro-web-app-routing-research.md)를 따른다.

여기서 논의하는 회사·팀 조직, 프로젝트·환경별 파일 관리, 배치 경로, 변수별 편집, 보관·버전 이력은 모두 **유료 Pro 범위**다. 무료 웹의 파일 공유·실시간 전달 기능과 사용자 흐름은 이 설계의 변경 대상이 아니다.

## 현재 상태와 순서

현재 구현 버전은 `0.0.1`이다. 웹의 암호화 파일 공유와 실시간 relay가 로컬에서 동작하고 `pnpm check`를 통과한다. 2026-09-24에 공개 URL의 화면과 `/api/health` 응답을 확인했고, 당시 화면 HTML의 해시가 배포에 사용한 웹 빌드와 일치했다. 이는 제품 단계 v1.0·v2.0의 핵심 기능 구현과 배포를 뜻하지만, 출시 완료를 뜻하지 않는다. 서로 다른 두 기기, 지원 브라우저, Cloudflare 무료 한도와 장애 시 동작은 아직 검증해야 한다. [웹 설계](web-design.md), [제품 계획의 완료 기준](product-plan.md#10-구현-순서와-검증)

웹 v2.0 출시 조건을 확인한 뒤 v3.0 Pro 베타를 구현한다. v3.0은 유료 제품 범위의 베타에 가깝고, 제품 내 결제·구독 기능은 만들지 않는다. 지속 보관과 결제·구독은 v3.0의 팀 권한·키 신뢰·임시 보관을 검증한 다음 v4.0에서 추가한다. 베타 참여자에게 실제 요금을 받을지와 받는다면 제품 밖에서 어떻게 처리할지는 별도 운영 결정이다.

무료 화면과 `/pro`는 같은 웹 빌드·배포물이므로 **웹 구현 버전은 하나**로 관리한다. 현재 `0.0.1`에서 이어 올리되 Pro가 시작한다고 `/pro`용 패키지 버전을 따로 `0.0.1`로 만들지 않는다. 이 문서의 v3.0·v4.0은 제품 기능 단계이며 배포 버전과 다르다. 별도 Node API와 후속 설치형 앱은 각각 독립 배포물이 생길 때 자체 버전을 둔다. 무료·Pro 화면을 독립 배포해야 할 이유가 생기면 그때 웹 버전도 분리한다.

v3.0 구현 후 무료 웹에도 도움이 되는 로컬 기능은 개별 검토해 적용할 수 있다. 예를 들어 Git 루트 기준 배치 경로 안내, `.env` 변수별 편집과 변경 미리보기, 파일·오류 안내 개선은 계정이나 서버 보관 없이 제공 가능하다. JSON·YAML의 파일 단위 공유는 무료 웹의 기존 파일 공유와 겹친다. 조직·팀 권한, 로그인 기반 요청함, 비동기 임시 보관, 지속 버전 이력은 Pro API가 필요한 기능으로 유지한다. 무료로 옮길 때는 기존 암호화 파일 형식과 계정 없는 흐름, Cloudflare 무료 한도를 각각 확인한다.

v3.0 베타에는 공개 셀프 회원가입을 열지 않는다. 계정 발급·초대는 운영자가 허용한 경로로 제한한다. 로그인한 Pro 사용자가 비회원에게 공유하는 흐름은 별도로 검토한다. 비회원에게 조직·프로젝트 권한을 주지 않고, 특정 시점의 파일 사본만 전달한다.

## 사용자 경로와 배포

| 주소·클라이언트 | 역할 |
| --- | --- |
| `https://envhandoff.mabyko.com/` | 무료 공유와 실시간 전달. 현재 Cloudflare 정적 웹·relay 유지 |
| `https://envhandoff.mabyko.com/pro` | 같은 웹 빌드의 Pro 화면. 로그인, 팀·프로젝트, 요청, 암호문 업로드·수신·버전 탐색 |
| `https://envhandoff-api.mabyko.com` | 별도 Node API. 계정, 구독, 팀 권한, 요청, 암호문 보관, 버전·접근 기록 |
| 후속 설치형 앱 | 같은 Pro API를 사용. 로컬 프로젝트 폴더 비교·적용·복구가 필요할 때 제공 |

Pro 웹은 정적 화면을 Cloudflare에서 받고, 데이터 요청은 브라우저에서 Pro API로 직접 보낸다. Pro API 요청은 무료 relay Worker를 통과하지 않는다. 브라우저의 CORS 허용 출처는 `https://envhandoff.mabyko.com`으로 제한한다. 쿠키 세션을 택한다면 API 호스트 전용 보안 쿠키, `credentials: 'include'`, 정확한 허용 출처와 자격 증명 응답, 요청 출처 검사를 함께 설계한다. 구독과 팀 권한은 화면 표시 여부와 무관하게 API의 모든 관련 작업에서 검사한다. [CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS), [OWASP 접근 제어](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)

## 단계별 기능

| 단계 | Pro 웹에서 제공할 것 | 서버 보관 | 설치형 앱의 역할 |
| --- | --- | --- | --- |
| v3.0 | 계정·팀·환경별 권한, 초대·요청, 승인 후 암호문 업로드와 비동기 수신 | 전달 완료 또는 만료까지 임시 보관 | 웹으로 다루기 어려운 로컬 폴더 작업을 검증한 뒤 추가 |
| v4.0 | 게시된 암호문 스냅샷의 지속 보관, 버전 탐색·복원, 접근 기록, 구독 | 버전·권한·과금 상태를 지속 관리 | 같은 저장소에 접근하고 로컬 프로젝트에 안전하게 적용·복구 |

Pro에서 관리하는 파일은 `프로젝트 + 환경 + 배치 경로`로 구분한다. 배치 경로는 팀이 정한 Git 저장소 루트 기준 상대 경로(예: `apps/api/.env.development`)다. 받는 화면에는 저장소 루트부터의 위치를 보여준다. 사용자마다 다른 로컬 절대 경로는 팀 데이터로 공유하지 않는다.

같은 파일을 **원본 파일 업로드**와 **변수별 편집** 두 방식으로 다룬다. 별도의 파일 목록을 만들지 않는다. 업로드한 원본 바이트는 그대로 보관하고, 변수별 편집을 시작할 때는 내용을 안전하게 읽을 수 있는 `.env` 파일인지 확인한다. 수정 후에는 변경된 줄과 결과 파일을 미리 보여주고, 해석할 수 없는 구문이나 원본 값이 달라질 위험이 있으면 변수별 저장을 막고 파일 전체를 다시 올리도록 안내한다. 현재 무료 웹의 변수 입력은 새 `.env` 파일을 만드는 기능일 뿐, 업로드한 파일을 읽어 서식을 보존하며 편집하는 기능은 아직 없다. [현재 입력 구현](../apps/web/src/lib/env.ts)

JSON·YAML(`.json`, `.yaml`, `.yml`) 설정 파일도 같은 프로젝트·환경의 파일 목록에서 업로드·공유하고, v4.0부터 변경 이력을 남긴다. 첫 Pro 범위에서는 이 파일들의 내부 항목을 개별 편집하지 않는다. JSON·YAML 항목별 편집은 각 형식의 값·주석·서식을 안전하게 다루는 방식을 검증한 뒤 후속 업데이트에서 추가한다.

버전 이력은 합의한 대로 v4.0의 지속 보관 범위다. 이 단계에서는 업로드와 변수별 수정 모두 **새 불변 스냅샷**을 만들고 이전 버전을 남긴다. 현재 최신 버전과 사용자가 편집을 시작한 버전이 다르면 덮어쓰지 않고 충돌을 알린다. v3.0은 임시 전달이므로 장기 이력을 보장하지 않는다.

v4.0 버전은 사용자에게는 **환경 전체의 한 시점**으로 보이게 한다. 저장소에서는 각 버전이 파일별 암호문을 참조하도록 설계한다. 변경하지 않은 파일은 기존 암호문을 다시 참조하고, 변경한 파일만 새 암호문을 저장한다. 예를 들어 1 MiB 파일 세 개 중 하나만 바꿔 열 버전을 만들면 단순 전체 복사에서는 약 30 MiB, 파일 참조 방식에서는 약 12 MiB와 작은 버전 정보가 필요하다. 변경한 파일은 그 파일 전체를 새로 저장하며 줄 단위 차분·압축이나 회사 간 중복 제거는 초기 범위에 넣지 않는다. 보관량 제한은 실제 유지하는 암호문 바이트를 기준으로 정한다.

현재 무료 공유 형식 v1은 여러 파일을 하나의 암호문으로 묶으므로 위 저장 방식을 그대로 제공하지 않는다. Pro의 파일별 암호화·버전 참조·기기별 키 접근은 v3.0의 기기 신뢰·복구 설계와 함께 검증해야 한다. [현재 파일 형식](bundle-format-v1.md)

## 화면 구조

기존 무료 홈에는 `Pro` 진입 링크를 둔다. `/pro`는 같은 사이트의 정적 경로이며 화면 코드 자체는 공개된다. 로그인·구독·팀 권한을 통과한 데이터와 작업만 API가 제공한다. 기존 무료 보내기·가져오기는 로그인 없이 계속 접근한다. 현재 앱은 해시 기반의 홈·보내기·가져오기 상태만 다루므로 `/pro`의 경로 이동·뒤로 가기·새로고침 복원은 구현 범위에 포함한다.

| 경로 | 화면 | 핵심 행동 |
| --- | --- | --- |
| `/pro` | Pro 시작 | 로그인 상태에 따라 소개, 팀 선택 또는 요청함으로 이동 |
| `/pro/requests` | 요청함 | 받은 요청과 내가 보낸 요청을 나눠 보고 상태·만료 시각 확인 |
| `/pro/requests/:id` | 요청 상세 | 수신자·프로젝트·환경 확인, 승인/거절, 파일 선택·암호화·업로드 또는 수신 |
| `/pro/projects` | 프로젝트 | 팀의 프로젝트·환경 목록과 내 접근 권한 확인 |
| `/pro/projects/:id` | 프로젝트 상세 | 환경별 권한과 최근 전달 확인; v4.0부터 게시된 버전 목록 |
| `/pro/team` | 팀 관리 | 초대, 멤버·환경 권한, 승인된 기기 확인 |
| `/pro/settings` | 내 설정 | 계정, 승인된 브라우저·기기, 복구 상태; v4.0부터 구독 |

처음에는 `워크스페이스 이름` 하나만 받는다. 내부적으로 조직과 기본 팀을 함께 만들되, 팀이 하나인 동안에는 팀 선택과 기본 팀 이름을 보여주지 않고 새 프로젝트에 기본 팀 접근 권한을 자동으로 준다. 설정에서 두 번째 팀을 추가할 때 기존 팀 이름을 확인·변경할 수 있게 하고, 그때부터 팀 선택과 프로젝트별 팀 접근 설정을 보여준다. 기존 프로젝트의 접근 권한은 팀 추가만으로 넓어지지 않는다. 기본 탐색은 `요청함 / 프로젝트 / 팀 관리`로 두고, 계정·기기 설정은 사용자 메뉴에 둔다. 요청 상세 URL은 새로고침과 초대 링크에서 복원되도록 한다. URL에는 파일 이름·복호화 키·공유 코드를 넣지 않는다. 모바일에서는 같은 정보와 행동을 세로로 배치하고, 핵심 작업은 키보드와 파일 선택 버튼으로도 가능하게 한다. 현재 웹의 밝은·어두운 화면과 시각적 방향을 이어 간다. [현재 웹 화면](../apps/web/src/App.tsx)

첫 방문에서는 `팀이 없음`, `초대 대기`, `브라우저 승인 필요`, `요청 없음`을 별개 상태로 보여준다. 특히 로그인 성공을 파일 복호화 가능 상태로 표시하지 않는다. 요청 수의 갱신은 숫자만 바꾸지 않고 문장으로 알리며, 실패한 입력은 해당 필드와 요약 위치에서 이유와 재시도 방법을 보여준다.

## 주요 작업 흐름

### v3.0: 요청하고 나중에 받기

1. 수신자가 팀의 프로젝트·환경을 고르고 보유자에게 파일을 요청한다. 화면에는 요청 대상, 받는 사람, 만료 예정 시각을 확인시킨다. 상태는 `승인 대기`다.
2. 보유자는 요청 상세에서 수신자와 환경을 확인하고 승인 또는 거절한다. **승인만으로 파일이 준비되지는 않는다.** 승인 후 `파일 업로드 대기`를 표시한다.
3. 실제 파일을 가진 보유자의 브라우저에서 사용자가 파일을 선택한다. 기존 파일 형식과 경로·크기 검사를 재사용하고 브라우저에서 암호화한 뒤 암호문만 업로드한다. 업로드 중에는 진행률과 취소를, 실패하면 원인을 보여주고 재시도를 제공한다.
4. API가 업로드를 완료해 `수신 가능`으로 바꾼다. 수신자는 나중에 접속해 권한과 기기 신뢰를 확인한 뒤 암호문을 받아 전체 인증을 마치고 원본을 다운로드한다. 이때만 `수신 확인`으로 표시한다. 다운로드는 로컬 프로젝트 적용 완료를 뜻하지 않는다.
5. 요청 취소, 권한 회수, 만료, 다른 수신자의 접근은 다운로드 전에 API가 거부한다. 이미 내려받은 파일과 키를 원격으로 지운다고 표시하지 않는다. [제품 계획의 상태·회수 규칙](product-plan.md#8-v30-팀-공유임시-보관)

요청 목록에서는 `승인 대기 / 파일 업로드 대기 / 수신 가능 / 수신 확인 / 거절 / 취소 / 만료`를 문자로 표시한다. 같은 요청의 중복 승인·업로드는 새 전달을 만들지 않고 현재 결과를 보여준다. 네트워크 오류가 나도 요청 상세로 돌아가 현재 서버 상태를 다시 확인할 수 있어야 한다.

### v4.0: 게시하고 버전 받기

권한자가 프로젝트 환경의 현재 버전을 확인하고 새 파일을 선택해 암호화·게시한다. 서버의 최신 버전이 그 사이 바뀌었다면 게시를 중단하고 두 버전을 보여준다. 게시가 끝난 스냅샷은 불변이며, 권한자는 필요할 때 이전 버전을 내려받을 수 있다. `복원`은 과거 버전을 덮어쓰는 동작이 아니라, 확인을 거쳐 그 내용을 **새 버전으로 게시**하는 동작이다. 접근 기록은 서비스가 관찰한 업로드·다운로드·권한 변경만 표시한다. [제품 계획의 버전 규칙](product-plan.md#9-v40-유료-클라우드-보관과-보안-운영)

## 데이터와 권한 경계

기본 관계는 `조직 → 팀`, `조직 → 프로젝트 → 환경`이다. 프로젝트에는 접근할 팀을 지정하고, 환경에는 그 안에서 실제 파일을 받거나 보낼 수 있는 권한을 둔다. 조직 안에 팀이 하나뿐이어도 내부 관계는 같고 기본 팀 권한을 자동으로 설정한다. 요청은 누가 어떤 환경의 파일을 필요로 하는지, 전달은 승인된 특정 스냅샷이 업로드·수신됐는지를 기록한다. API는 모든 목록·상세·업로드·다운로드·초대·권한 변경에서 현재 사용자의 조직·팀·환경 권한을 다시 검사한다. 웹이 버튼을 숨기는 것은 권한 검사가 아니다. 서버에 보일 수 있는 조직·팀 관계·파일 크기·접근 시각 등의 메타데이터는 제품 설명에 명시한다. [제품 계획의 도메인과 보안](product-plan.md#8-v30-팀-공유임시-보관)

웹에서는 사용자가 파일을 선택해 암호화하고, 받은 파일을 확인·다운로드한다. 브라우저가 프로젝트 폴더에 자동 적용·복구한다고 약속하지 않는다. 해당 동작은 브라우저 지원과 파일 권한을 별도 검증해야 하며, 설치형 앱의 명확한 가치로 남긴다. [MDN 폴더 접근 지원](https://developer.mozilla.org/en-US/docs/Web/API/Window/showDirectoryPicker)

서버는 계정·조직·팀 관계·권한·전달 상태와 암호문을 저장한다. Pro v3.0부터 로그인은 필수이며 로그인으로 계정과 서버 접근 권한을 확인한다. 파일 평문과 복호화 키는 서버가 받지 않는다. 따라서 로그인이나 비밀번호 재설정으로 잃어버린 브라우저·기기의 복호화 키가 복원되지는 않는다. v3.0의 기기 등록·공개키 신뢰·첫 기기 연결·키 변경 알림은 웹 브라우저에도 동일하게 적용해야 한다. 다른 승인 기기로 새 기기를 승인하거나 별도로 보관한 복구 수단을 사용하는 절차가 필요하다. 모든 기기와 복구 수단을 잃었다면 기존 암호문은 열 수 없으며, 접근 가능한 팀원이 파일을 다시 게시해야 한다. 브라우저 저장소가 지워지거나 기기를 바꿨을 때의 복구 경로를 확정하기 전에는 팀 암호문 보관 기능을 출시하지 않는다. [제품 계획의 v3.0 보안 조건](product-plan.md#8-v30-팀-공유임시-보관)

## 구현 전 결정할 것

1. 브라우저를 승인된 기기로 등록하고 공개키를 검증하는 절차, 모든 기기 분실 시 복구 절차.
2. 웹 세션과 설치형 앱 인증 방식. 두 클라이언트 모두 같은 팀 권한·구독 판정을 받아야 한다.
3. v3.0 임시 파일의 저장소·삭제 기한, v4.0 지속 보관과 결제 실패 시 내보내기 정책.
4. v3.0 Pro 베타의 참여 범위와 운영 방식. 제품 내 결제·구독은 v4.0부터 구현한다. 베타에서 실제 요금을 받을지와 제품 밖 수납 방식은 아직 정하지 않았다.
5. 웹 Pro와 후속 앱이 현재 relay를 사용할지. 현재 relay는 `Origin` 헤더를 요구하므로 설치형 앱 연결은 별도 검증이 필요하다. [현재 Worker](../apps/server/src/index.ts)
6. 비회원 공유를 무료 파일·코드 전달로 시작할지, Pro API가 암호문을 짧게 보관하는 게스트 링크까지 v3.0에 넣을지. 게스트 링크라면 로그인한 권한자가 브라우저에서 선택한 파일을 별도로 암호화해 게시하고, 비회원은 해당 사본만 열 수 있어야 한다. 링크 소지자의 신원은 확인되지 않으며 만료·회수는 아직 내려받지 않은 사본에만 유효하다.

## v5.0 검토안: 선택형 관리 복구

기본 Pro는 서버가 파일을 읽을 수 없는 암호화 방식을 유지하고, 복구 수단 보관은 조직의 책임으로 둔다. v5.0에서 조직이 명시적으로 신청하는 추가 유료 옵션으로 복구키 위탁을 검토한다. 복구키를 같은 운영자가 관리하는 별도 서버에 두는 것만으로 서버의 복호화 능력이 없어지지는 않는다. 운영자가 복구키와 암호문에 모두 접근할 수 있다면 해당 옵션은 기본 Pro와 다른 보안 약속으로 설명해야 한다. 이 경우 복구 승인, 운영자 접근 통제·기록, 키 분실·유출, 옵션 해지와 과거 버전 처리까지 설계한 뒤 출시 여부를 결정한다. 보관 바이트보다 운영·보안 책임이 요금의 근거가 될 수 있으나 가격은 미정이다. [OWASP 키 관리](https://cheatsheetseries.owasp.org/cheatsheets/Key_Management_Cheat_Sheet.html)
