# EnvHandoff Pro 웹 설계

작성일: 2026-09-24. 갱신일: 2026-09-28. 이 문서는 Pro 웹의 화면·사용자 흐름과 v4.0 이후 방향을 설명한다. 출시 단계는 [제품 계획](product-plan.md), **v3.0 권한·기기·전달·보관·오류·검증의 단일 기준은 [v3.0 구현 명세](pro-v3-spec.md)**다. 배포 방향의 근거는 [조사 결과](pro-web-app-routing-research.md)를 따른다.

## 현재 상태와 순서

현재 웹 구현 버전은 `0.0.1`이다. 암호화 파일 공유와 실시간 relay를 구현했고 기존 `pnpm check` 통과와 2026-09-24 공개 화면·`/api/health`·당시 배포 빌드의 HTML 일치를 확인했다. 공개 테스트 배포와 정식 출시는 구분한다. 실제 두 기기, 지원 브라우저, 무료 한도·장애 검증은 남아 있다. [웹 설계](web-design.md), [제품 계획의 완료 기준](product-plan.md#10-구현-순서와-검증)

Git 저장소 루트 기준 배치 경로 안내와 기존 `.env`의 안전한 변수 편집·변경 미리보기는 현재 코드에 구현되어 있다. 2026-09-28 관련 자동 테스트 6개 통과를 확인했다. 이 확인은 해당 변경의 공개 배포·전체 브라우저 검증을 뜻하지 않는다. 새 `.env` 생성과 기존 파일 편집은 구분하며, 모호한 형식은 파일 전체를 다시 선택하도록 안내한다. Pro는 이 클라이언트 기능을 전달 준비에 재사용한다.

웹 v2.0 출시 조건 확인 후 v3.0 Pro 웹의 무료 초대 베타를 진행한다. 팀원 요청과 비회원 수신을 함께 제공한다. 제품 안팎 모두 요금을 받지 않으며, 결제·구독·지속 버전은 v4.0 웹에서 추가한다. 네이티브 앱은 v4.0 웹 검증 후 연결한다. Pro는 유료 제품군의 이름이며 현재 베타의 과금을 뜻하지 않는다.

무료 화면과 `/pro`는 같은 빌드·배포물이므로 웹 구현 버전은 하나다. Pro가 시작한다고 별도 패키지 버전을 `0.0.1`로 다시 만들지 않는다. v3.0·v4.0은 제품 단계이며 배포 버전·공유 파일 형식 버전과 다르다. 별도 API와 후속 설치형 앱은 독립 배포물로 자체 버전을 둔다.

## 사용자 경로와 배포

| 주소·클라이언트 | 역할 |
| --- | --- |
| `https://envhandoff.mabyko.com/` | 계정 없는 무료 공유와 기존 실시간 relay |
| `https://envhandoff.mabyko.com/pro` | 같은 정적 웹 빌드의 Pro 관리 화면 |
| `https://envhandoff.mabyko.com/receive/:id` | 비회원의 특정 사본 수신 |
| `https://api.envhandoff.mabyko.com` | 별도 Node API. 계정·권한·요청·암호문 임시 보관 |
| v4.0 네이티브 앱 | 같은 Pro API와 로컬 프로젝트 비교·적용·복구 |

Pro API 요청은 무료 relay Worker를 통과하지 않는다. API의 쿠키 세션·정확한 origin 허용·CSRF 방어·권한 검사와 비회원 토큰 규격은 구현 명세를 따른다. v3.0에는 베타 참여 상태와 팀 권한을 검사하고 구독은 v4.0부터 검사한다. Pro relay 통합은 v3.0에 넣지 않는다. 무료 relay는 기존 화면에서 계속 사용한다.

## 화면 구조

현재 `/pro`는 시작·초대 화면이며 요청함·프로젝트·외부 공유·팀 관리·내 설정을 아래 경로로 분리했다. 조직은 `?org=<UUID>`로 지정하고, 생략하면 현재 접근 가능한 첫 조직으로 주소를 정규화한다. 프로젝트 환경에서 요청·외부 공유를 시작하면 `environment=<UUID>&create=1`로 선택을 전달한다. 기존 `/pro?org=<UUID>&request=<UUID>` 또는 `share=<UUID>` 링크도 새 상세 경로로 정규화한다. 로그인 후 복귀·뒤로 가기·새로고침과 이동 시 작업 손실 확인을 연결했다.

무료 홈에는 `Pro` 진입 링크를 둔다. 현재 앱은 메모리 상태로 홈·보내기·가져오기를 전환하고 relay 수신 링크만 해시를 사용한다. Pro에는 경로·뒤로 가기·새로고침 복원을 추가한다. 기존 `#receive/...` 링크를 유지하고 Pro 외부 링크와 구분한다. 화면 코드는 공개되며 API가 실제 데이터·작업 권한을 검사한다.

| 경로 | 화면 | 핵심 행동 |
| --- | --- | --- |
| `/pro` | Pro 시작 | 로그인, 개설 초대·멤버 초대 수락, 조직 선택, 첫 기기 안내 |
| `/pro/requests` | 요청함 | 받은 요청·내 요청, 현재 상태와 과거 수신 확인 표시 |
| `/pro/requests/:id` | 요청 상세 | 승인/거절, 파일 준비·업로드, 수신, 취소·회수, 새 요청 |
| `/pro/shares` | 외부 공유 | 공유 생성, 내 공유 목록; Owner는 조직의 운영 상태 확인 |
| `/pro/shares/:id` | 외부 공유 상세 | 상태·기한·수신 보고, 링크 재발급·회수. 잃은 코드는 복원하지 않음 |
| `/receive/:id` | 비회원 수신 | 링크 토큰과 별도 코드로 파일 열기·다운로드 |
| `/pro/projects` | 프로젝트 | 접근 가능한 프로젝트·환경 목록, Owner의 생성 |
| `/pro/projects/:id` | 프로젝트 상세 | 환경·권한 관리, 파일 요청·외부 공유 시작, 본인 관련 최근 전달 |
| `/pro/team` | 팀 관리 | Owner의 초대·팀 구성·프로젝트 연결·역할 관리, 조직 내 기기 상태 확인·접근 회수 |
| `/pro/settings` | 내 설정 | 계정, 등록 기기·추가 기기 승인·등록 해제·분실 안내 |

워크스페이스는 조직의 화면상 이름이다. 처음에는 이름 하나를 입력하고 기본 팀은 숨긴다. 두 번째 팀을 추가할 때 기존 팀 이름을 확인하고 팀 선택·프로젝트 연결 UI를 연다. 기본 팀의 프로젝트 접근과 환경별 파일 권한은 별개이며, 새 환경에서는 Owner가 필요한 사용자의 권한을 명시적으로 정한다.

기본 탐색은 `요청함 / 프로젝트 / 외부 공유 / 팀 관리`, 조직 전환·계정·기기는 사용자 메뉴에 둔다. 생성·초대·기기 확인은 기존 화면과 대화상자를 재사용한다. 원래 상세 링크는 로그인 후 복원하되 현재 권한을 다시 검사한다. URL에 파일 이름·복호화 키·공유 코드를 넣지 않는다. 요청 기한, 전달 이용 기한, 삭제 처리 기한을 구분해 설명한다.

모바일은 같은 정보와 행동을 세로로 배치하고, 핵심 작업은 키보드와 파일 선택 버튼으로도 가능하게 한다. 요청 수 갱신은 문장으로 알리고 실패 원인·재시도 방법을 필드와 요약 위치에 표시한다. 현재 밝은·어두운 화면과 시각적 방향을 이어 간다. [현재 웹 화면](../apps/web/src/App.tsx)

## v3.0 주요 흐름

### 팀원에게 요청하고 나중에 받기

수신자가 환경·요청할 멤버를 고르고 현재 수신 기기에 묶인 요청을 만든다. 지정 송신자가 승인하고 상대 기기 키를 확인한 뒤 로컬 파일을 선택·편집·암호화해 업로드한다. 승인만으로 파일이 준비되지는 않는다. 업로드가 확정되면 송신자가 접속하지 않아도 지정 수신자가 원래 기기에서 열고 다운로드할 수 있다.

첫 전달에는 별도 대화 경로에서 상대 공개키를 확인한다. 등록 기기 추가는 기존 기기로 승인하되 과거 파일 키를 자동 이전하지 않는다. 새 기기에서 기존 파일이 필요하면 새 요청으로 재전송받는다. 요청 가능한 멤버가 파일을 실제 보유한다고 보장하지 않으며, 파일이 없으면 거절할 수 있다.

화면은 요청 상태·전달 이용 가능 상태·수신 확인 기록을 구분한다. ‘수신 확인됨 · 만료됨’도 함께 표시한다. 수신 확인은 저장·프로젝트 적용의 증거가 아니다. 요청 기한·취소·재시도·권한 회수의 정확한 효과는 [구현 명세](pro-v3-spec.md)를 따른다. 알림은 요청함과 상세 링크 직접 전달이며 자동 메일·푸시는 제공하지 않는다.

### 비회원에게 보내기

외부 공유 권한자가 로컬 파일을 별도 코드로 암호화해 올리고, 링크와 코드를 서로 다른 대화 경로로 전달한다. 비회원은 로그인·팀 초대·기기 등록 없이 사본만 연다. 링크·코드 소지자의 실제 신원은 보장하지 않는다.

공유 코드는 생성한 탭에서만 다시 볼 수 있다. 탭을 닫기 전에 코드를 전달하도록 안내하고, 분실하면 기존 공유를 회수하고 새로 만든다. 공유 상세에서 서버 상태는 복원할 수 있지만 코드는 복원할 수 없다. 링크 재발급은 이전 토큰을 무효화하며 코드를 바꾸거나 이용 기한을 연장하지 않는다. 방문·다운로드 시작·수신 확인만으로 토큰을 소모하지 않는다.

### 파일 준비와 오류

v3.0은 전달별 사본을 관리하며 환경의 공식 최신 파일 목록은 제공하지 않는다. 업로드 전 기존 `.env` 편집과 새 파일 생성은 같은 전달 준비 목록으로 이어진다. JSON·YAML은 파일 단위로만 공유한다. 같은 환경·경로라도 다른 전달의 내용이 같거나 최신이라고 가정하지 않는다. 로컬 절대 경로는 공유하지 않는다.

로그인 성공·브라우저 등록·상대 키 확인·복호화 가능 상태를 구분한다. 참여 불가, 초대 대기, 요청 없음, 키 없음, 코드 분실, 업로드 실패, 결과 불명, 만료·회수에 각각 원인과 가능한 다음 행동을 표시한다. 새로고침은 서버 상태만 복원하고 로컬 파일·편집 내용·코드를 복원하지 않는다. 이동 전 작업 손실을 안내한다. Pro 장애에도 무료 파일 공유로 이동할 수 있지만 자동 전송은 하지 않는다.

## v4.0 지속 보관과 네이티브 앱

v4.0은 지속 보관·환경 버전 탐색·복원·사용자용 접근 기록·구독을 추가한다. v3.0의 기본 운영 보안 기록은 이미 필요한 별도 기능이다. 권한자가 게시한 불변 버전을 보관하고 편집 시작 버전과 서버 최신 버전이 다르면 게시를 중단한다. 복원은 과거 버전을 변경하지 않고 확인 후 새 버전으로 게시한다.

v4.0 버전은 사용자에게는 **환경 전체의 한 시점**으로 보이게 한다. 저장소에서는 각 버전이 파일별 암호문을 참조하도록 설계한다. 변경하지 않은 파일은 기존 암호문을 다시 참조하고, 변경한 파일만 새 암호문을 저장한다. 예를 들어 1 MiB 파일 세 개 중 하나만 바꿔 열 버전을 만들면 단순 전체 복사에서는 약 30 MiB, 파일 참조 방식에서는 약 12 MiB와 작은 버전 정보가 필요하다. 변경한 파일은 그 파일 전체를 새로 저장하며 줄 단위 차분·압축이나 회사 간 중복 제거는 초기 범위에 넣지 않는다. 보관량 제한은 실제 유지하는 암호문 바이트를 기준으로 정한다.

위 용량 예시는 암호화·직렬화 오버헤드를 제외한 근사치다. v3.0은 묶음 단위 전달이며 파일별 참조는 v4.0에서 도입한다. 환경 버전의 인증된 파일 목록, 파일 삭제·이름 변경·일괄 게시, 새 권한자의 키 접근과 퇴사 후 향후 버전 키 정책을 함께 설계한다. 기존 v3.0 전달을 자동으로 지속 버전으로 바꾸지 않는다.

웹은 파일을 다운로드하고 사용자가 직접 배치한다. 로컬 프로젝트 비교·적용·복구는 후속 네이티브 앱의 역할이다. 앱 인증·OS 키 저장·relay 연결은 앱 착수 때 검증하며 v3.0의 선행 작업으로 만들지 않는다.

## v5.0 검토안: 선택형 관리 복구

기본 Pro는 서버가 파일을 읽을 수 없는 암호화 방식을 유지하고, 복구 수단 보관은 조직의 책임으로 둔다. v5.0에서 조직이 명시적으로 신청하는 추가 유료 옵션으로 복구키 위탁을 검토한다. 복구키를 같은 운영자가 관리하는 별도 서버에 두는 것만으로 서버의 복호화 능력이 없어지지는 않는다. 운영자가 복구키와 암호문에 모두 접근할 수 있다면 해당 옵션은 기본 Pro와 다른 보안 약속으로 설명해야 한다. 이 경우 복구 승인, 운영자 접근 통제·기록, 키 분실·유출, 옵션 해지와 과거 버전 처리까지 설계한 뒤 출시 여부를 결정한다. 보관 바이트보다 운영·보안 책임이 요금의 근거가 될 수 있으나 가격은 미정이다.
