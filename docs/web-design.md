# 웹 우선 구현과 모노레포 구성

갱신일: 2026-09-11. 상태: 웹 0.0.1의 일반 파일 공유와 로컬 실시간 relay 구현. 루트와 workspace package.json 버전은 0.0.1이다. 제품 기능 단계 v1.0·v2.0 및 파일 형식 버전 1과 구분한다. React + TypeScript + Vite, Turborepo + pnpm을 사용하며 실제 배포와 여러 기기·브라우저 검증은 후속 작업이다.

제품 단계와 파일 보호 원칙은 [제품 계획](product-plan.md), 후속 데스크톱의 직접 적용·복구는 [데스크톱 설계](app-design.md), 용어는 [CONTEXT.md](../CONTEXT.md)를 따른다.

## 1. 첫 출시 범위

웹에서 v1.0 일반 공유를 먼저 완성하고 v2.0 실시간 relay까지 첫 배포에 포함한다. D의 단계별 안내와 시각적 방향을 사용하되, 첫 웹에서는 사용자 파일을 선택·암호화하고 받은 파일을 확인·다운로드하는 데 집중한다.

- 일반 공유: 사용자가 선택한 파일을 브라우저에서 암호화해 `.envhandoff`로 다운로드한다. 사용자는 AirDrop·기존 메신저·이메일 첨부 등으로 이 파일을 전달한다.
- 받기: 공유 파일과 별도 공유 코드로 전체 암호문 인증을 마친 뒤 경로·파일 목록을 확인한다. 내용은 요청한 경우에만 표시하고, 사용자가 선택한 원본 파일을 개별 다운로드한다.
- 실시간 전달: 암호화 묶음을 준비하고 연결 링크를 개인 대화로 전달한다. 송신자가 상대를 확인하고 승인하면 Cloudflare relay로 암호문을 보낸다. 양쪽 탭이 열려 있어야 하며 수신자의 전체 암호문 인증 응답을 받아야 완료다.
- 계정·이메일 인증·자동 메일 발송·서버 파일 보관은 v2.0에 포함하지 않는다. 파일 복호화 코드는 별도 경로로 전달한다.

첫 웹에는 프로젝트 폴더 자동 배치, Git 상태 검사, 덮어쓰기·백업·복구가 없다. 수신 화면은 `파일 다운로드`라고 표시하고, 프로젝트에 적용했다고 표현하지 않는다. 사용자가 다운로드한 평문 사본은 앱이 보관·복구하는 캐시와 구분한다.

일반 파일 선택·다운로드를 기준으로 데스크톱 Chrome·Edge·Safari·Firefox를 검증한다. 폴더 직접 쓰기와 OS 공유 창 연동은 같은 지원 범위라고 가정하지 않는다. 폴더 쓰기 API에는 브라우저별 지원과 권한 제약이 있다. [MDN 폴더 접근 문서](https://developer.mozilla.org/en-US/docs/Web/API/Window/showDirectoryPicker)

## 2. 첫 사용자 흐름

보내기: `파일 보내기` → 파일 선택·공유 경로 확인 → 프로젝트 표시명·환경 이름 → 공유 방식 선택 → 암호화 묶음 준비 → 파일 다운로드 또는 연결 링크 전달.

받기: `파일 가져오기` 또는 연결 링크 열기 → 공유 파일 수신 → 코드 입력·암호문 인증 → 파일 목록·필요한 내용 확인 → 개별 파일 다운로드.

- 파일 선택을 취소하면 기존 작업을 유지한다. 기본 공유 경로는 파일명으로 두고 하위 경로가 필요하면 사용자가 명시해 확인하는 안으로 시작한다. 브라우저에서 제공되지 않은 로컬 절대 경로를 추측하지 않는다.
- 공유 경로는 파일 이름과 별도로 표시하고, 중복·경로 탈출·지원하지 않는 경로는 묶음 생성과 열기 모두에서 거부한다. 첫 구현에서 이 규칙을 파일 규격과 함께 고정한다.
- 다운로드 목록에는 원래 공유 경로를 표시한다. 다운로드한 파일을 그 경로에 직접 배치하는 것은 수신자의 행동이며, 앱은 배치 완료를 알 수 없다.
- 잘못된 코드·변조·크기 제한 실패 시 파일 내용이나 다운로드를 제공하지 않는다. 설정 파일 내용은 실행하거나 HTML로 해석하지 않는다.
- 파일·코드·내용·현재 선택은 작업 메모리에 둔다. 새로고침·탭 종료 후 자동 복원하지 않고, 키를 URL·로그·분석 이벤트·영구 브라우저 저장소에 넣지 않는다.
- 실시간 전송률 100%는 `수신 확인 대기`다. 연결 종료·취소·확인 시간 초과는 중단으로 처리하고 새 연결 재전송 또는 일반 파일 공유로 이어진다.

## 3. 모노레포 구성

현재 웹·relay·공통 프로토콜·공개 테스트 벡터를 구성했다. 실행 명령과 검증 범위는 [README](../README.md)를 따른다. 데스크톱은 후속 작업이다.

```text
apps/
  web/                  웹 화면과 브라우저 파일·암호화 처리
  server/               Cloudflare Workers + Durable Objects relay
  desktop/              예정: 후속 Tauri 앱과 Rust 코어
packages/
  protocol/             함께 쓰는 연결 메시지·검증 규칙
fixtures/
  bundles/              공개 가능한 가짜 데이터와 파일 호환성 테스트 벡터
docs/
```

Turborepo + pnpm workspaces로 시작한다. Node.js 24.21.0과 pnpm 12.3.4는 `mise.toml`, Turborepo 2.10.12는 루트 `package.json`에 고정했다. 프로젝트마다 실행·검사·빌드 명령과 의존성을 선언하고, 루트에서 Turborepo로 실행한다. JS/TS 의존성 잠금 파일은 공유하되 후속 Rust 코드는 Cargo로 빌드한다. 공통 패키지는 내부 의존성으로 연결하며 npm 배포를 전제로 하지 않는다. [pnpm workspaces](https://pnpm.io/workspaces)

| 도구 | 맡는 일 | 현재 선택 |
|---|---|---|
| pnpm workspaces | 의존성 설치, 내부 패키지 연결, 프로젝트별 명령 실행 | 사용 |
| Turborepo | 작업 의존 순서와 결과 캐시 | 처음부터 사용 |
| Bun 패키지 매니저 | pnpm 대신 의존성 설치와 workspace 관리 | 대안으로 검토, 초기에는 pnpm 사용 |
| Nx + pnpm | 작업 실행·캐시, 생성기, 프로젝트 관계와 의존 규칙 관리 | 현재 필요한 관리 기능이 적어 보류 |
| Lerna + pnpm | 패키지 버전·npm 배포, Nx 기반 작업 실행 | 공개 패키지 배포 요구가 없어 보류 |

Turborepo·Nx·Lerna는 pnpm과 같은 종류의 선택지가 아니다. pnpm workspaces 위에 필요한 작업 도구를 얹을 수 있다. 비교 근거: [Turborepo 캐시](https://github.com/vercel/turborepo/blob/main/apps/docs/content/docs/crafting-your-repository/caching.mdx), [Nx 기능](https://nx.dev/docs/features), [Lerna 버전·배포](https://lerna.js.org/docs/features/version-and-publish), [Lerna와 Nx](https://lerna.js.org/docs/lerna-and-nx).

Bun도 workspaces와 의존성 격리를 지원하고 Turborepo와 함께 쓸 수 있다. Bun을 설치 도구로 쓰면서 개발 도구는 Node.js로 실행하는 구성도 가능하다. 이 프로젝트는 브라우저·Cloudflare Workers·후속 Rust 앱이 실행 환경이므로 Bun 런타임 도입이 필수는 아니다. 초기에는 Node.js LTS와 pnpm으로 개발 환경을 맞추는 쪽을 택했다. 설치 속도의 우열은 이 저장소에서 측정하지 않았다. [Bun workspaces](https://bun.com/docs/pm/workspaces), [Bun 의존성 격리](https://bun.com/docs/pm/isolated-installs), [Bun 설치 도구](https://bun.com/docs/pm/cli/install), [Turborepo workspace 구성](https://github.com/vercel/turborepo/blob/main/apps/docs/content/docs/crafting-your-repository/structuring-a-repository.mdx).

웹과 서버는 빌드·배포를 따로 구성한다. 공통 규약 변경은 관련 클라이언트와 함께 검사하되, 같은 저장소에 있다는 이유로 이미 배포된 클라이언트와의 호환성을 생략하지 않는다. Cloudflare도 프로젝트별 빌드·배포 설정을 가진 모노레포를 지원한다. [Cloudflare 모노레포 문서](https://developers.cloudflare.com/workers/ci-cd/builds/advanced-setups/#monorepos)

파일 규격과 테스트 벡터를 웹과 후속 Rust 코어가 함께 사용한다. 서버가 알아야 할 연결 메시지와 크기 제한을 파일 복호화 동작과 분리하고, 서버는 복호화 키를 받지 않는다. UI 패키지는 두 클라이언트에서 실제로 함께 사용할 화면이 생길 때 추출한다.

## 4. 0.0.1에서 확정한 구현 항목

1. 웹 구성: React + TypeScript + Vite. D 시안의 중앙 앱 형태를 유지하고, 바깥 여백과 내부 열을 화면 너비에 맞춘다. 560px 이하에서는 앱을 화면 너비에 맞추고 입력과 카드가 한 열로 흐른다. 700·800px에서도 고정된 축소 비율 없이 내용 너비에 따라 배치한다.
2. 파일 형식: [파일 형식 v1](bundle-format-v1.md)에 24바이트 헤더, AES-256-GCM, 키 인코딩, JSON 필드, 크기·경로·오류 규칙을 고정했다. 독립적인 Node 암호 구현으로 만든 공개 벡터와 브라우저 왕복으로 검증한다.
3. 웹의 파일 경로·다운로드: 일반 파일 선택과 수정 가능한 상대 경로를 사용한다. 전체 인증 전에는 파일 목록과 내용을 제공하지 않는다. 개별 파일 다운로드는 원본 바이트를 보존하며, 내용 보기는 기본적으로 닫혀 있다. 원본 파일 배치는 사용자가 직접 한다.
4. 실시간 relay: [relay 프로토콜](relay-protocol.md)에 역할별 토큰, 송신 승인, 64 KiB 조각과 한 조각씩의 수신 응답, 10분 세션, 30초 전송 대기, 2분 열기 대기, 요청 제한과 재사용 방지를 고정했다. 서버에는 요청 제한 카운터만 저장한다.

후속 데스크톱에 남은 완료 백업 진입, 부모 폴더 처리, Git 검사 실패 등 기존 설계 검토 항목은 데스크톱 착수 전에 해결한다. 웹에 직접 적용 기능을 조용히 추가하거나 기존 데스크톱의 보호 조건을 완화해서 해결하지 않는다.

## 5. 첫 구현의 완료 증거

첫 작업은 D의 시작 화면에서 가짜 파일을 고르고, 암호화 공유 파일을 만든 뒤 코드로 다시 열어 원본 바이트를 확인하는 흐름이다. 잘못된 코드·변조·잘린 파일을 거부하는 검사와 지원 브라우저에서의 파일 입력·다운로드 확인을 함께 수행한다. 사용자의 실제 설정 파일과 코드는 테스트 자료·로그·빌드 캐시에 넣지 않는다.

0.0.1에서는 일반 파일 공유 왕복과 로컬 relay의 두 탭 전달을 확인했다. 100% 전송과 인증 후 수신 완료를 구분하며, 잘못된 코드에서는 다운로드와 완료 응답을 제공하지 않는다. 원본 바이트 비교와 경계 검사는 자동 테스트로도 실행한다. 현재의 통과 결과는 전체 보안 감사나 실제 배포 검증을 대신하지 않는다. 실제 두 기기·지원 브라우저·Cloudflare 무료 한도와 장애를 검증한 뒤 웹 파일럿을 진행한다.
