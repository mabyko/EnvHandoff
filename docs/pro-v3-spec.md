# EnvHandoff v3.0 Pro 웹 구현 명세

작성·갱신일: 2026-09-28. 상태: **Pro 기능 구현 후 추가로 발견한 감사·삭제 지연 감지·긴급 중지 도구 보완 완료. 브라우저·실기기 QA와 운영 구성 전**.

이 문서는 v3.0의 권한·기기·전달·보관·실패 처리를 정하는 단일 기준이다. [제품 계획](product-plan.md)은 출시 단계, [Pro 웹 설계](pro-web-design.md)는 화면과 후속 방향을 설명한다. 상세 규칙을 바꿀 때는 이 문서를 먼저 수정하고 두 문서의 요약을 맞춘다. 무료 파일 규격은 [파일 형식 v1](bundle-format-v1.md)을 따른다.

2026-09-28 검토 후 사용자가 결정 위임한 사항에 아래 기본안을 채택했다. 이전 합의와 이번 선택을 구분하기 위해 결정 이유를 함께 기록한다. 기술 검증이 필요한 항목을 구현 완료나 보안 검토 완료로 해석하지 않는다.

## 1. 범위와 이번에 채택한 결정

2026-09-29 배포 방향: v3 코드와 자체 호스팅 설치 문서는 공개 저장소에 유지한다. 공식 클라우드는 무료 초대 베타로 운영하고, v4 추가 기능·유료화는 별도 비공개 저장소에서 개발한다. 설치 경로와 외부 서비스 의존성은 [자체 호스팅 가이드](self-hosting.md)를 따른다. LICENSE와 재배포·경쟁 호스팅 허용 범위는 아직 미결정이다.

| 항목 | 개발 기준 | 이유 |
| --- | --- | --- |

| 외부 공유 코드 | 생성한 탭의 메모리에서만 제공. 분실 시 기존 공유 회수 후 새 공유 | 서버나 송신 기기용 코드 복구 저장소를 추가하지 않음 |

팀원 요청과 비회원 수신은 모두 첫 베타에 포함한다. 보관 선택은 기존 합의대로 24시간·3일·7일, 기본 24시간이다. 자동 메일·푸시, 자동 동기화, 서버 평문 처리, 로컬 프로젝트 직접 적용, JSON·YAML 항목 편집, 결제·지속 버전·파일 키 복구는 범위 밖이다. 운영자가 확인한 관리 역할 복구는 3절 범위에 포함한다. 실시간 전달이 필요하면 기존 무료 화면을 사용하며 Pro의 팀 권한이 무료 relay까지 적용된다고 표시하지 않는다.

## 2. 배포와 인증

무료 웹과 `/pro`, `/receive/:id`는 같은 웹 빌드·버전을 사용한다. Pro 데이터는 브라우저에서 `https://api.envhandoff.mabyko.com`의 별도 Node API로 직접 요청한다. 무료 Worker는 Pro API 프록시나 인증 서버가 아니다. Pro API 장애가 무료 파일 공유를 막지 않아야 한다.

GitHub 로그인은 계정 확인만 담당한다. 내부 사용자 ID와 공급자의 계정 식별자를 연결하고 표시 이름·로그인 이름·이메일을 권한의 식별자로 쓰지 않는다. GitHub 저장소 권한을 요구하지 않는다. 사용할 OAuth 앱 유형·최소 scope·콜백 검증·토큰 폐기 방식은 구현 시 공식 문서로 검증한다. 공급자 토큰을 Pro 웹의 세션 토큰으로 사용하지 않는다.

API 호스트 전용 `Secure; HttpOnly; SameSite=Lax` 쿠키와 서버 세션을 사용한다. 상위 도메인에 쿠키를 공유하지 않는다. 웹 요청은 credentials를 포함하며 CORS는 운영 웹의 정확한 origin만 허용한다. 개발 origin은 개발 설정에만 둔다. 변경 요청은 정확한 Origin 검증과 세션에 연결된 CSRF 검증을 거친다. OAuth 콜백은 해당 로그인 거래의 state 등 공급자가 지원하는 보안 절차로 별도 검증한다. 임의 외부 URL로 로그인 후 돌아가게 하지 않는다.

세션은 비활성 12시간·절대 7일에 만료한다. 로그인 시 세션 식별자를 교체하고, 로그아웃·계정 중지 시 서버에서도 무효화한다. Owner 이전·추가 기기 승인·기기 회수·조직 삭제는 최근 15분 이내 재인증을 요구한다. 역할·환경 권한을 세션 생성 당시 값으로 고정하지 않고 매 요청에서 현재 상태를 확인한다. v3.0에는 구독 검사가 없으며 조직의 베타 참여 상태를 검사한다.

## 3. 조직과 초대

워크스페이스는 UI에서 사용하는 조직 이름이다. GitHub 로그인은 공개하지만 직접 개설은 운영자 또는 베타 코드를 활성화한 계정만 가능하다. 두 경우 모두 최대 2개 워크스페이스를 소유할 수 있다. 팀 초대만 받은 계정은 직접 개설할 수 없으며 Owner 승격도 베타 자격을 부여하지 않는다. 다른 팀 가입에는 해당 팀의 초대가 필요하다. Owner 승격·이전·관리 복구에도 소유 한도를 적용하며 중지된 조직의 남아 있는 Owner 관계도 센다. 삭제로 소속이 제거되면 한도가 반환된다.

운영자 권한은 서버의 `PRO_OPERATOR_GITHUB_ID`와 GitHub가 검증한 숫자 ID의 일치로 결정한다. 첫 로그인·표시 이름·클라이언트 입력으로 운영자 권한을 얻을 수 없다. `/pro/beta`에서 운영자는 최근 본인 확인 후 인원(1~1,000명)·유효 일수(1~365일)를 지정해 코드를 발급·취소한다. 발급 중인 코드는 최대 100개다. 코드는 128비트 난수이며 원문은 발급 응답에서만 표시하고 DB에는 해시만 저장한다. 유효 기간과 취소는 신규 활성화만 막으며, 이미 활성화된 계정의 자격은 유지된다. 계정당 활성화는 한 번이고 동시 사용·재시도로 인원을 초과하거나 중복 차감하지 않는다. 실패한 입력도 계정별 10분 20회 한도에 포함한다.

기존 운영자 개설 초대로 승인된 계정은 마이그레이션에서 베타 자격을 보존한다. 기존 개설 초대 CLI는 자체 호스팅 호환 경로로 유지하며 수락 시 같은 소유 한도를 적용한다. 신규 클라우드 참여는 베타 코드 화면을 사용한다. v4 무제한 워크스페이스는 유료 혜택 후보이며 아직 구현하지 않는다.

Owner/Member는 **조직 역할**이며 팀별 Owner는 두지 않는다. 조직 가입과 팀 소속은 별도다. Owner가 프로젝트·환경·팀 생성과 이름 변경, 팀 연결, 멤버 초대·제외, 환경 권한을 관리한다. 기본 팀 하나일 때는 팀 선택 UI를 숨기고 새 프로젝트를 기본 팀에 연결한다. 이 연결은 메타데이터 접근만 부여하며 파일 받기·보내기·외부 공유 권한은 자동으로 주지 않는다. 환경 생성 시 Owner가 자신을 포함해 필요한 사용자의 권한을 명시적으로 설정한다.

멤버 초대는 특정 GitHub 계정과 조직·대상 팀에 묶고 7일 후 만료한다. 로그인 이름으로 대상을 찾더라도 발급 시 계정 식별자를 확정한다. 대상이 다르면 소비하지 않고 올바른 계정으로 로그인하도록 안내한다. 취소·만료·재사용을 검사하고 같은 계정의 중복 수락은 같은 가입 결과를 반환한다. 초대만으로 환경 권한이나 기기 신뢰는 생기지 않는다. 수락 전 초대자가 Owner 자격을 잃으면 초대를 취소한다. 초대 링크는 기존 메신저로 전달한다.

팀 추가로 기존 프로젝트 접근이 넓어지지 않는다. 팀 제거·탈퇴 후에도 다른 팀을 통해 동일 프로젝트 접근이 유지되면 유효 권한은 유지한다. 마지막 조직 Owner의 탈퇴·강등은 다른 멤버에게 Owner를 부여한 뒤에만 허용한다. 모든 Owner가 계정 접근을 잃으면 운영자가 베타 온보딩 때 등록한 연락 경로로 조직을 재확인해 관리 역할만 복구한다. 기존 세션·미완료 초대를 폐기하고 사건을 기록하며, 기기 키·파일 복호화 신뢰는 복구하지 않는다.

## 4. 권한과 조회 범위

조직 소속이 유효하고, 사용자의 소속 팀 중 하나 이상이 프로젝트에 연결되어 있고, 해당 사용자에게 환경의 해당 작업 권한이 명시되어야 파일 작업을 허용한다. 환경 권한은 `받기 / 보내기 / 외부 공유`의 독립된 허용 값이며 기본값은 모두 거부다. 팀 권한과 사용자 권한을 별개의 경로로 합쳐 조직 경계를 우회하지 않는다. Owner도 파일 작업에는 같은 조건을 적용한다.

| 작업 | 허용 조건 |
| --- | --- |
| 조직·팀·프로젝트·환경 관리 | 해당 조직 Owner |
| 기기 등록·추가 승인·전역 회수 | 본인 계정만 가능. 추가 승인은 기존 기기의 확인도 필요 |
| 프로젝트·환경 기본 정보 조회 | 연결된 팀 멤버 또는 관리 목적의 조직 Owner |
| 요청 생성 | 받기 권한과 등록된 현재 수신 기기. 보내기 권한이 있는 멤버 한 명 지정 |
| 요청 승인·거절·업로드 | 지정 송신자와 현재 보내기 권한. 업로드에는 신뢰 확인한 송신 기기 필요 |
| 팀원 암호문·키 정보 다운로드 | 지정 수신자, 현재 받기 권한, 요청에 고정한 수신 기기의 키 소유 증명, 이용 가능한 전달 |
| 외부 공유 생성 | 현재 외부 공유 권한. 로컬 파일을 코드로 암호화하므로 송신 기기 등록은 필수 아님 |
| 외부 공유 다운로드 | 그 공유의 접근 토큰, 현재 공유 상태, 생성자의 외부 공유 권한·조직 상태 |
| 전달 회수 | 송신자·지정 수신자 또는 조직 Owner. 외부 공유는 생성자 또는 Owner |

요청·팀원 전달의 목록과 상세는 참여 당사자와 조직 Owner에게만 보인다. Owner는 운영 메타데이터와 상태를 볼 수 있으나 암호문·파일 키 다운로드 권한은 자동으로 얻지 않는다. 외부 공유 목록은 생성자와 Owner에게만 보인다. 비회원은 조직·멤버·프로젝트·환경 목록에 접근하지 않는다. 같은 환경의 다른 수신 권한자도 타인의 전달을 받지 못한다. 송신자에게 서버 사본을 다시 내려받는 별도 권한을 제공하지 않는다. 재전송에는 자신이 보유한 원본 또는 이미 정당하게 받은 사본을 사용한다.

기기 키는 사용자에 속하며 여러 조직에서 사용할 수 있다. 조직 Owner는 자기 조직의 전달에 사용된 기기 상태를 확인하고 조직 권한·전달을 회수할 수 있지만, 타인의 기기를 다른 조직까지 전역 회수하거나 개인키를 삭제하지 못한다. 본인의 전역 기기 회수는 그 기기에 연결된 모든 조직의 전달에 적용한다.

요청 대상은 ‘파일 보유자’가 아니라 ‘요청 가능한 멤버’다. 권한만으로 파일 보유를 판단하지 않는다. 파일이 없으면 거절하고 기존 대화로 다른 담당자를 안내한다. 파일 요청은 해당 환경에서 송신자가 선택한 한 묶음을 대상으로 하며 환경 전체의 완전성을 보장하지 않는다. 특정 파일 목록 협의는 기존 대화로 하고 v3.0에는 자유 입력 요청 본문을 저장하지 않는다.

## 5. 기기 등록과 상대 키 확인

기기는 물리적 컴퓨터가 아니라 사용자 계정에 연결한 브라우저 프로필의 키다. 새 브라우저·새 프로필·사이트 데이터 삭제 후에는 새 기기로 등록한다. 로그인, 조직 권한, 기기 등록, 상대 공개키의 신뢰 확인을 별개로 취급한다.

| 경우 | 절차 |
| --- | --- |
| 첫 Owner 또는 멤버의 첫 기기 | 브라우저에서 키를 생성하고 서버에 공개키·소유 증명을 등록. 등록 자체로 상대가 신뢰하지 않음 |
| 상대의 첫 기기와 처음 전달 | 양쪽이 기존에 신원을 아는 별도 대화 경로에서 계정·기기·공개키 지문을 대조하고 로컬에 고정 |
| 자신의 추가 기기 | 기존 등록 기기가 새 기기의 계정·공개키·일회성 확인 요청을 확인해 승인 증명을 만듦 |
| 추가 기기와 상대방의 첫 전달 | 베타에서는 상대도 새 기기 지문을 별도 대화로 다시 확인. 승인 증명만으로 자동 신뢰하지 않음 |
| 모든 기기 분실 | 계정 재인증 후 이전 기기를 모두 회수하고 새 키 등록. 상대와 지문 재확인 후 새 요청 |
| 기존 기기의 키 변경 | 같은 기기 ID에 키를 덮어쓰지 않고 새 기기로 등록. 자동 수락 금지 |

등록된 자기 키가 없는데 서버가 임의의 기존 키를 보여줘도 복구된 것으로 간주하지 않는다. 상대 키 지문은 API 응답과 같은 경로에서 확인하는 것만으로 완료하지 않는다. 처음 서로 확인할 기존 연락 경로가 없는 사람끼리의 팀원 전달은 베타에서 지원하지 않는다. 비회원 전달은 링크·코드 방식이며 팀원 신뢰 절차의 대체 수단이라고 표시하지 않는다.

요청은 생성한 **수신 기기 하나**에 고정한다. 송신자는 업로드 전에 해당 기기의 고정된 키를 확인한다. 수신자는 열기 전에 발신 기기를 확인한다. 새 기기 승인으로 과거 전달 키를 다시 배포하지 않는다. 새 기기에서 파일이 필요하면 새 요청으로 재전송받는다. 이미 수신 가능한 이전 전달은 원래 기기에서 기한 내 계속 받을 수 있고, 기기를 분실했다면 회수한다. 원본 보유자와 기존 복호화 수단이 모두 없으면 복구할 수 없다.

기기 소유·추가 승인·회수·분실 복구의 암호 증명과 영속 상태는 [기기 신뢰 v1](device-trust-v1.md)을 따른다. 기기별 ECDH·ECDSA 키와 계정·기기 ID를 함께 지문에 묶고 별도 경로로 확인한다. 로그인·HTTP 연결과 전달별 다운로드 소유 증명, 회수의 요청/전달 연쇄 종료는 아직 16절의 선행 검증 대상이다. 별도 경로 확인이 있는 정상 클라이언트의 키 바꿔치기 탐지를 목표로 하며, 악성 서버의 모든 기록 은폐·롤백을 탐지하는 전역 키 투명성 시스템을 제공한다고 약속하지 않는다.

## 6. 브라우저 키와 작업 데이터

기기 개인키는 내보낼 수 없는 브라우저 키 객체로 생성·보관하는 방식을 우선 검증한다. 계정별로 분리한 로컬 저장소에 기기 키·확인한 상대 지문만 보관하고 평문 파일·공유 코드·복호화된 묶음 키는 영구 저장하지 않는다. 브라우저·프로필 접근자나 같은 origin의 악성 스크립트까지 막는 OS 보안 저장소와 동등하다고 설명하지 않는다. 지원 브라우저에서 안전한 보관과 재사용을 검증하지 못하면 실제 비밀값을 다루는 팀원 베타를 열지 않는다.

로그아웃·계정 전환·세션 만료 시 진행 중 작업을 중단하고 메모리의 파일·코드·복호화 결과를 비운다. 다른 열린 탭에도 종료를 알린다. 기기 키는 해당 계정의 다음 로그인에 재사용하되 다른 계정으로 사용하지 못하게 한다. ‘이 브라우저 등록 해제’는 서버 회수와 로컬 키·신뢰 기록 삭제를 함께 수행한다. 오프라인 로컬 삭제와 원격 회수 미완료를 구분해 표시한다. 원격 회수는 로컬 키가 삭제되었다는 보장이 아니다.

공유 PC에서는 기기 등록을 권하지 않는다. 비공개 모드·저장소 사용 불가·키 소실은 명시적으로 알리고 메모리 키를 장기 등록 성공으로 표시하지 않는다. 승인 요청의 기기 이름·브라우저 정보는 사용자를 돕는 표시이며 키 소유 증명을 대신하지 않는다.

## 7. 파일과 암호화 계약

v3.0 파일의 범위는 `전달 + 배치 경로`다. 경로는 Git 저장소 루트 기준 상대 경로이며 클라이언트가 [v1 경로·크기 규칙](bundle-format-v1.md#크기와-공유-경로)을 생성·수신 양쪽에서 검사한다. 같은 환경·경로에 여러 전달 사본이 있을 수 있고, 환경의 최신 파일이나 영구 경로 목록을 만들지 않는다. 업로드 전 원본 선택·안전한 `.env` 값 편집을 재사용한다. 변경하지 않은 원본은 바이트를 보존하며, 수정본은 사용자 확인 후 전달할 파일로 교체한다. 서버의 기존 사본을 덮어쓰지 않는다.

팀원 전달은 묶음 단위 암호문과 지정 기기용으로 암호화한 묶음 키, 발신 인증 정보를 보관한다. 기존 v1의 원본 바이트·경로 검증을 재사용하되 팀 외피는 별도 형식 식별자를 사용한다. v1 파서에 알 수 없는 필드를 끼워 넣지 않는다. 비회원 공유는 기존 v1과 새 공유 코드를 사용한다. 팀원 전달에서 공유 코드를 서버에 보내거나 계정 로그인만으로 키를 복구하지 않는다.

팀 외피는 최소한 형식 버전·조직/프로젝트/환경 ID·요청/전달 ID·발신 사용자/기기·수신 사용자/기기·암호문과 키 정보의 결합을 암호학적으로 검증해야 한다. 다른 요청의 정상 암호문·키 정보 교환도 거부한다. 서버의 가변 접근 상태와 클라이언트가 인증한 불변 내용을 구분한다. 팀 전달의 바이트 배치·HPKE Auth 키 감싸기·ID와 암호문 결합·오류·공개 벡터는 [팀 전달 외피 v1](team-envelope-v1.md)에 고정한다. 기기 소유·승인·회수 증명은 [기기 신뢰 v1](device-trust-v1.md)에 정의하고 별도 검증한다. 구현자가 자체 암호 프로토콜을 임의로 조합해서는 안 된다.

서버는 평문 내부의 파일 수·확장자·경로·문법을 검사할 수 없다. 서버는 바깥 요청·권한·암호문 바이트 제한·완료 상태를 검사하고, 수신자는 전체 인증과 내부 유효성 검사 후에만 파일 목록·다운로드를 제공한다. 서버의 업로드 완료는 파일 내용의 유효성 증명이 아니다. 입력 파일을 실행하거나 HTML로 해석하지 않는다.

## 9. 요청·전달·ACK

요청 기한은 생성부터 **7일 안에 최초 전달의 업로드 확정을 끝내는 기한**이다. 승인만으로 기한이 연장되지 않는다. 기한 안에 확정하면 요청은 fulfilled가 되고 이후 이용 가능 여부는 전달 보관 기한과 회수·현재 권한으로 판단한다. 예를 들어 요청 6일째 업로드하고 7일 보관을 선택하면 업로드 확정부터 7일 동안 받을 수 있다.

```text
Request: pending -> approved / rejected / cancelled / expired
         approved -> fulfilled / cancelled / expired
Upload attempt: uploading -> committed / failed / cancelled
Transfer: available -> expired / revoked
ACK: acknowledgedAt을 별도로 기록; Transfer 상태와 보관 기한은 유지
```

업로드 시도는 전달 준비 작업이다. 실제 바이트·키 정보가 모두 저장되고 현재 권한·기기·요청 기한을 다시 확인한 뒤 전달을 available로 확정한다. 요청마다 확정 전달은 하나이며 DB 제약과 상태 비교로 동시 업로드를 막는다. 외부 공유는 Request 없이 동일한 업로드·전달 확정을 사용한다. 사용자에게 업로드 진행률과 실패·취소·재시도를 제공한다.

| 동작 | 결과 |
| --- | --- |
| pending 거절 | 지정 송신자만 가능. rejected로 종료 |
| pending/approved 요청 취소 | 요청자·지정 송신자·Owner가 가능. cancelled, 활성 업로드도 중단 |
| 업로드만 취소·실패 | 시도만 종료. 요청은 기한·권한이 유효하면 approved에서 새 시도 가능 |
| 요청 기한 도달 | 미이행 요청을 expired로 처리하고 진행 중 확정 거부 |
| 업로드 확정 | 요청 fulfilled, 전달 available, 서버 시각으로 보관 기한 시작 |
| 이행 후 종료 | 요청을 과거 상태로 되돌리지 않고 전달 revoked. 화면 행동은 ‘전달 회수’ |
| 전체 인증·검사 성공 보고 | 지정 수신 기기 또는 외부 공유 토큰의 ACK. 최초 시각만 기록 |
| 잘못된 코드·인증·내부 형식 실패 | ACK 없음. 재입력 또는 송신자 재전송 안내 |

ACK는 클라이언트의 보고이며 파일 저장·프로젝트 적용·비회원 신원을 증명하지 않는다. 악성 클라이언트의 허위 보고도 막았다고 표현하지 않는다. 화면은 ‘수신 확인됨 · 만료됨’처럼 현재 이용 가능 상태와 과거 ACK를 함께 보여준다. ACK를 이유로 사본을 삭제하거나 기한을 연장하지 않는다.

승인·취소·업로드 확정·회수는 경쟁 시 하나의 유효 결과만 남도록 상태를 조건부 변경한다. 취소 또는 권한 회수가 먼저 확정되면 뒤늦은 업로드 완료로 되살리지 않는다. 다운로드를 이미 시작한 바이트는 회수할 수 없으며, 연결을 종료할 수 있어도 원격 삭제를 약속하지 않는다.

## 10. 재시도와 비회원 공유

요청·전달·외부 공유의 업로드 시도와 변경 작업에는 호출자가 생성한 작업 식별자를 사용한다. 동일 식별자·동일 대상·동일 내용의 재시도는 같은 결과를 반환하고, 내용이 다르면 충돌로 거부한다. 멱등 결과를 반환하기 전에도 현재 접근 권한을 검사한다. 보관 기한은 최초 확정 시각에서 다시 시작하지 않는다.

업로드 성공 응답이 유실되면 작업 상태를 조회한다. 확정 전 실패는 파일 전체를 처음부터 다시 올리고, 부분 이어 올리기는 제공하지 않는다. 페이지를 닫아 메모리의 파일·암호문을 잃으면 파일을 다시 선택해 새 시도를 시작한다. 이전 시도의 취소·만료와 용량 정리를 거친다. 확정 후 파일 변경·수신 기기 변경은 새 요청으로 처리한다.

비회원 링크는 `/receive/:id#token=<접근 토큰>`으로 한다. 토큰은 복호화 코드와 독립된 256비트 무작위 값이며 생성 브라우저에서 만들어 서버에는 해시를 등록한다. 수신 페이지는 fragment를 읽어 주소에서 제거하고 메모리에서만 사용하며 API 요청 헤더로 전송한다. 링크 원문·헤더 토큰을 로그·분석 도구·리퍼러에 남기지 않는다. 토큰을 잃은 새로고침은 원래 링크를 다시 열도록 안내한다. 방문이나 다운로드 시작으로 토큰을 소모하지 않고 명시적으로 파일 열기를 선택한 뒤 받는다.

공유 코드는 생성한 탭을 유지하는 동안만 다시 볼 수 있다. 공유 상세의 서버 상태를 복원해도 코드는 복원하지 않는다. 닫기·이동 전에 별도 경로로 코드를 전달하도록 안내한다. 코드를 잃으면 원본에서 새 코드·새 암호문으로 공유를 만들고 기존 공유를 회수한다. 서버에는 코드 복구 API를 만들지 않는다.

접근 링크 원문도 서버에서 다시 읽지 않는다. 생성자는 유효한 공유에서 ‘링크 재발급’을 선택해 새 토큰 해시로 원자적으로 교체할 수 있다. 기존 링크는 즉시 무효화되며 코드·암호문·기한은 그대로다. 응답이 유실되어도 탭에 남은 새 토큰으로 동일 작업을 재시도할 수 있다. 토큰까지 잃으면 다시 재발급한다. Owner는 회수할 수 있지만 생성자를 대신해 링크를 발급하지 않는다.

## 11. 회수와 삭제

현재 권한은 모든 작업에서 검사한다. 파일 다운로드 권한이 없더라도 당사자는 자기 요청·전달의 최소 종료 상태를 확인하고 회수할 수 있다. 종료 상태 확인이 파일명·키·다른 멤버 정보를 노출하지 않게 한다.

| 사건 | 기존 요청·전달의 처리 |
| --- | --- |
| 수신자의 유효 받기 권한 또는 조직 소속 상실 | 미이행 요청 취소, 해당 수신자의 유효 전달 회수 |
| 송신자의 유효 보내기 권한 또는 조직 소속 상실 | 미이행 요청 취소, 그 송신자의 해당 환경 유효 전달 회수 |
| 외부 공유 생성자의 외부 공유 권한 상실 | 해당 환경의 유효 외부 공유 회수 |
| 요청 수신 기기 회수 | 그 기기에 묶인 미이행 요청 취소·유효 전달 회수 |
| 팀원 전달 발신 기기 회수 | 그 기기로 업로드한 유효 전달과 진행 중 업로드 회수. 승인만 한 요청은 새 기기로 업로드 가능 |
| 다른 기기 회수 | 연결되지 않은 전달에는 영향 없음. 기기와 무관한 외부 공유는 별도로 회수 |
| 환경·프로젝트·조직 삭제, 계정 중지 | 해당 범위의 미이행 요청·초대·업로드 취소, 유효 전달 회수 |
| 권한 재부여·재가입 | 이전 cancelled/revoked 항목은 복원하지 않음. 새 요청·공유 필요 |

팀 소속 변경은 최종 유효 권한의 상실 여부로 판단한다. 권한 상실과 해당 요청·전달의 논리적 종료를 같은 DB 거래에서 확정하고 물리적 객체 삭제만 비동기로 처리한다. 권한을 즉시 다시 부여해도 종료 처리 전에 다운로드가 열리는 틈을 만들지 않는다. 명시적 회수는 서명·암호문을 수정하지 않고 서버 접근 상태를 종료한다. 이전 키를 가진 사람의 로컬 사본을 없애거나 실제 서비스 자격증명을 폐기하지는 못한다.

암호문 이용 기한은 업로드 확정부터 선택한 24시간·3일·7일이다. 만료·회수 순간 새 다운로드를 차단하고 활성 저장소의 암호문·암호화된 묶음 키·접근 토큰 해시를 **24시간 안에 삭제**한다. ‘최대 7일’은 다운로드 가능 기한이며 삭제 처리에는 추가 최대 24시간이 필요함을 업로드 화면에 설명한다. 실패 업로드는 시작 후 최대 1시간에 종료하고 종료 후 24시간 안에 잔여 객체를 삭제한다.

v3.0 암호문은 별도 백업·객체 버전 보관을 하지 않는다. 저장소의 자동 복제·삭제 보장도 위 기한에 맞는 구성을 검증한다. 메타데이터 DB 백업은 암호화해 최대 7일 보관하되 파일 키 정보·접근 토큰 해시는 백업 대상에서 제외한다. 재시작 때 정상 저장 데이터는 유지하지만, 재해 복원으로 이전 권한·회수 상태가 되돌아갈 가능성이 있으면 복원된 모든 활성 전달을 폐기하고 재전송을 요청한다. 오래된 백업만으로 전달 접근을 다시 열지 않는다.

요청·전달 종료 메타데이터와 최소 보안 기록은 종료 또는 사건 발생 후 30일 보관한다. 계정 삭제 시 활성 관계·공개키·초대는 24시간 안에 제거한다. 조직 삭제는 그 조직의 관계·초대를 제거하며 다른 조직에 사용하는 계정·기기 공개키는 삭제하지 않는다. 남는 보안 기록은 내부 식별자·사건·시각·결과만 유지하고 메타데이터 백업의 최대 7일 잔존도 안내한다. 정상 동작에 필요한 영구 삭제 표시는 백업 복원보다 우선 적용한다. 삭제 실패를 재시도·경보하고 완료되지 않았는데 삭제 완료로 표시하지 않는다.

## 12. 업로드와 운영 한도

초기 한도는 아래 값을 적용하고 버전 관리하는 서버 코드 설정으로 관리한다. 한도 조정은 설정 변경·재배포·회귀 검사를 거친다. 베타 관찰 후 조정할 수 있지만 자동 유료 확장이나 보안 제한 해제는 하지 않는다. 무료 relay의 한도와 별도로 계산한다.

| 항목 | 초기 한도 |
| --- | --- |
| 원본 파일 | v1과 동일: 파일당 1 MiB, 합계 10 MiB, 100개 |
| 업로드 | v1 공유 16 MiB. 팀 외피 v1은 16 MiB + 134바이트로 제한하며 전체 17 MiB 상한 이내 |
| 조직 멤버 / 사용자 기기 | 조직당 20명, 사용자당 등록 기기 5개 |
| 조직 보관량 | 확정 객체·업로드 예약·삭제 대기 객체 합계 512 MiB |
| 미이행 요청 / 동시 업로드 | 조직당 100건 / 3건 |
| 생성 빈도 | 사용자당 요청·공유·업로드 시도 합계 10분에 20건 |
| 다운로드 | 조직당 UTC 하루 1 GiB, 공유별 동시 다운로드 3개 |
| 비회원 조회·다운로드 시작 | IP당 분당 60회, 공유별 분당 30회. 실제 전송 바이트 제한도 별도 적용 |

최종 암호문 길이를 선언하고 업로드 전에 용량을 예약한다. 서버는 스트리밍 수신 중에도 실제 길이를 제한하고 선언 길이와 다르면 확정하지 않는다. 정리 전 객체의 공간을 곧바로 재사용한 것으로 계산하지 않는다. 다운로드도 전송 시작 전 크기를 예약해 동시 요청의 한도 우회를 막고 종료 후 실제 전송량으로 정산한다. 재시도·중단으로 전송한 바이트도 사용량에 포함한다.

업로드된 객체는 비공개·불변으로 두고 모든 다운로드는 API가 현재 권한을 확인한 후 중계한다. 장기 서명 URL, 공개 객체 URL, CDN 캐시를 사용하지 않는다. 민감 응답은 캐시하지 않는다. 저장소와 DB는 단일 거래라고 가정하지 않고 ‘객체 저장 → 조건부 확정 → 미참조 객체 정리’를 구현한다. 프로세스 종료·중복 완료·삭제 작업 실패를 포함해 검증한다. 최소 Node 서비스와 정리 작업으로 시작하며 별도 큐·분산 워크플로 엔진을 선제 도입하지 않는다.

## 13. 화면·오류·운영 기록

기본 탐색은 `요청함 / 프로젝트 / 외부 공유 / 멤버 · 팀`로 한다. 조직 전환과 계정·기기는 사용자 메뉴에 둔다. 팀 관리의 조직 변경 작업은 Owner만 실행한다. 프로젝트 상세에서 환경 생성·권한 설정·요청 생성·비회원 공유를 시작한다. 초대 수락과 첫 기기 확인은 첫 방문 흐름에 넣으며 상세 화면 또는 대화상자를 재사용한다. 핵심 행동은 키보드와 파일 선택 버튼으로도 가능하게 하고, 상태·오류는 색이나 숫자만으로 알리지 않는다.

로그인 후 원래 요청·공유 상세로 돌아오되 ID의 현재 조직·권한을 재검사한다. 조직 선택을 잘못했어도 URL의 대상 권한을 우회하지 않는다. 화면 경로와 서버 상태만 복원하고 로컬 파일·편집 내용·코드·진행 중 업로드가 복구된다고 표시하지 않는다. 이동·새로고침 전에 작업 손실을 안내한다. 기존 무료 relay의 `#receive/...` 링크와 Pro의 경로·fragment 처리를 분리해 호환성을 유지한다.

| 상태 | 안내·행동 |
| --- | --- |
| 참여 자격 없음 / 초대 대기 / 조직 없음 | 원인을 구분하고 로그인 반복으로 해결된다고 표시하지 않음 |
| 등록 필요 / 상대 키 확인 필요 | 각 확인 절차로 이동. 계정 권한 부족과 구분 |
| 현재 기기에 기존 파일 키 없음 | 원래 기기에서 열기 또는 새 요청으로 재전송 |
| 세션 만료 | 작업 중단·평문 제거 후 로그인, 서버 상태 재조회 |
| 업로드 실패 / 결과 불명 | 오류 원인과 현재 시도 조회, 미확정일 때만 재업로드 |
| 만료 / 회수 | 다운로드 불가. 당사자에게 상태·과거 ACK를 함께 표시 |
| 잘못된 외부 토큰·없는 ID | 리소스 존재·조직 정보를 구별할 수 없는 응답 |
| 한도 초과 | 제한과 재시도 시점 표시. 보관 기한 연장이나 무료 relay 자동 전환 없음 |

앱 내 요청함은 진입·탭 복귀·작업 후 새로 조회하고 전용 푸시 연결은 만들지 않는다. 사용자가 상세 링크를 기존 메신저로 전달한다. Pro 장애 시 무료 파일 공유로 이동할 수 있지만 파일·키를 자동 이동하거나 다른 공유 방식으로 무단 전송하지 않는다.

최소 보안 기록은 로그인·세션 종료·초대·기기 등록/회수·권한 변경·업로드 확정·다운로드 허용/거부·ACK·회수·삭제 실패를 담는다. 기록에는 사건·내부 대상 ID·시각·결과만 남기고 파일명·파일 내용·키·코드·토큰·요청/응답 본문을 남기지 않는다. 남용 제한용 IP 정보는 단기 집계로 최대 24시간만 보관한다. v4.0의 사용자용 접근 기록 화면과 구분한다. 운영자의 메타데이터 접근과 수동 복구·중지도 기록한다.

같은 origin의 무료 화면·Pro·비회원 화면을 모두 동일한 보안 경계로 다룬다. 외부 분석·세션 녹화 스크립트를 넣지 않고 입력 표시·콘텐츠 보안 정책·의존성·오류 보고의 비밀 노출을 함께 검토한다. 키 지문·사용자 파일을 테스트 데이터로 수집하지 않는다.

베타 정상 종료는 최소 7일 전에 알리고 신규 요청·업로드를 중지한 뒤 기존 전달은 원래 기한까지 제공한다. 침해나 계정 악용에 따른 긴급 중지는 즉시 접근을 차단하고 사유를 안내한다. 결제 실패 처리나 자동 유료 전환은 없다.

## 14. 구현 순서와 수용 검사

2026-09-28 추가 지시: 브라우저·사용자 수동 검증 단계는 남은 구현이 끝난 뒤 시작한다. 구현 중 자동 회귀·타입 검사·lint·빌드는 계속 수행한다.

2026-09-28 진행 방식: 기능 구현을 먼저 완료하고 사용자 수동 QA는 마지막에 모아서 진행한다. 남은 수동 검사와 발견한 문제·수정·재검사 결과는 [QA 기록](qa.md) 한 곳에 누적하며, 기능마다 사용자에게 즉시 검사를 요청하지 않는다. 자동 테스트와 브라우저로 검증할 수 있는 항목은 Codex가 실행하고, 검증 범위와 근거를 기록해 PASS로 처리한다. 미구현 항목은 구현 대기, 아직 실행하지 않은 검사는 에이전트 검증 대기로 구분한다. 사용자에게는 실제 패스키 인증 창과 인증 앱 QR 스캔 등 실제 장치에서만 확인할 부분을 마지막에 요청한다. 타입 검사·lint·빌드도 계속 수행하며, 일부만 검증한 항목 전체를 PASS로 간주하지 않는다.

1. 무료 웹 v2.0 출시 조건과 이번 문서의 권한표·상태 전이를 확인한다.
2. 가짜 파일로 첫 기기·상대 지문 확인·팀 외피·분실 재등록을 검증하고 기술 규격을 고정한다.
3. 로그인·조직·팀·환경 권한을 구현하고 API의 조직 경계 검사를 먼저 통과한다.
4. 요청 → 승인 → 업로드 → 송신자 종료 → 수신 → ACK → 재다운로드 → 만료를 완성한다.
5. 비회원 링크·코드 분리, 코드 분실·링크 재발급·회수를 완성한다.
6. 관리 화면과 한도·정리·재해 복원·브라우저 검증을 끝내고 무료 베타를 연다.

자동 검사는 가짜 파일·테스트 키로 실행하고 서버 시각·상태 경쟁·재시작을 재현한다. 실제 두 기기와 지원 브라우저 검증은 자동 단위 검사로 대신하지 않는다. 사용자 데이터로 암호 프로토콜을 시험하지 않는다.

## 15. v4.0 이후와의 경계

v4.0의 환경 전체 버전은 인증된 파일 목록과 파일별 암호문 참조로 구성한다. 파일 추가·삭제·이름 변경, 한 버전의 일괄 확정, 과거 복원, 새 권한자에게 기존 파일 키 배포, 퇴사 후 향후 버전 키 정책을 v4.0 착수 시 함께 설계한다. 같은 암호문을 참조한다고 새 기기에 키 접근권이 생기지는 않는다. 과거에 배포한 키의 원격 회수는 약속하지 않는다.

v3.0 임시 전달을 자동으로 지속 버전으로 승격하거나 유효 기한을 늘리지 않는다. v4.0 보관에는 권한자가 새로 게시해야 한다. v3.0 팀 외피와 v1 공유 읽기는 해당 형식의 지원 정책에 따라 유지한다. 네이티브 로그인·기기 저장소·relay 연결, 결제·지속 보관 가격, 조직 복구키·선택형 위탁 복구는 별도 후속 범위다.

## 16. 남은 기술 검증과 사용자 결정의 경계

현재 제품 정책에 사용자의 추가 응답을 기다리는 항목은 없다. 무료 베타·기기별 재요청·일회성 코드 제공·삭제 처리 기한 등은 이번 위임에 따라 채택한 기본안이며, 사용자가 다른 운영 요구를 주면 관련 규칙을 함께 변경한다.

다음은 개발자가 검증해 이 문서에 결과를 채워야 하는 **기술 선행 조건**이다. 미정인 채 실제 비밀값을 받는 베타를 열지 않는다.

- **암호 규격:** 검증된 프로토콜과 구현체 선정, 키 생성·보관·발신 인증·기기 소유 증명·서명 직렬화·nonce·오류·공개 테스트 벡터. 5~7절의 제품 흐름을 충족하는지 검토하며 수동 지문 확인을 생략하지 않는다.
- **로그인 연결:** GitHub의 현재 지원 방식·최소 권한·콜백·CSRF 방어를 공식 문서로 검증하고 지원 브라우저에서 세션을 확인한다.
- **배포 저장소:** DB 엔진은 사용자 결정에 따라 PostgreSQL로 확정했다. Node 호스팅·PostgreSQL 호스팅·비공개 객체 저장소의 실제 기존 자원과 예산을 확인해 하나씩 선정한다. 용량 예약·조건부 확정·재시작 지속성·삭제 24시간·백업 제외·복원 차단을 검증한다. 새 유료 계약·운영 계정 권한이 필요할 때 구체적인 비용·자원안을 준비해 사용자에게 요청한다.
- **출시 증거:** 14절의 실제 두 기기·지원 브라우저·장애·보안 검토 결과를 기록한다. 이번 문서 검토나 기존 `.env` 테스트 통과가 이 검증을 대신하지 않는다.

설계 참고: [OWASP 접근 제어](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html), [키 관리](https://cheatsheetseries.owasp.org/cheatsheets/Key_Management_Cheat_Sheet.html), [브라우저 저장소](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html), [CSRF 방어](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html), [세션 관리](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html). 구체적 도구 선정과 API 사용법은 구현 시 최신 공식 문서로 확인한다.

### 기술 선행 검증 진행 기록 — 2026-09-28

현재는 14절의 **5단계 외부 공유까지 구현하고 로컬 검증**했다. 6단계의 장애 주입·복원 차단 명령도 연결했으며 운영 저장소·실제 복원 훈련·지원 브라우저·출시 검증은 남아 있다. 아래 기록은 구현 순서에 따른 이력이다.

- `@hpke/core` 1.9.0의 RFC 9180 Auth 모드(P-256 / HKDF-SHA256 / AES-256-GCM)를 가짜 데이터로 검증했다. `apps/web/src/lib/team-crypto.ts`와 Node 테스트에서 비추출 개인키 왕복, 9개 결합 ID 각각의 변경, 다른 발신·수신 키, 암호문 변조 거부를 확인했다. `fixtures/bundles/team-v1.json`은 제품 코드와 HPKE 라이브러리를 사용하지 않는 Node `crypto` 보조 구현(`team-reference.mjs`)으로 재생성 가능한 공개 벡터다. 해당 벡터 열기와 인증된 위험 경로 거부를 확인했다. RFC 공식 벡터 전체 통과나 외부 보안 감사 완료를 뜻하지 않는다.
- `apps/web/src/lib/device-keys.ts`는 내부 사용자 UUID별로 비추출 기기 키를 IndexedDB에 저장한다. 기존 키는 덮어쓰지 않으며 같은 계정의 동시 생성은 하나만 성공한다. 삭제 시 기기 ID도 검사해 이전 탭이 새 기기를 지우지 못하게 한다. 읽기에서 키가 없으면 자동 생성하지 않는다. 로컬 저장·삭제는 서버 등록·회수 또는 상대방의 신뢰 확인을 대신하지 않는다.
- macOS의 격리된 Headless Chrome 153에서 페이지 새로고침 후 키와 지문 유지, 개인키 내보내기 거부, 저장된 발신·수신 키의 HPKE 왕복, 계정 분리, 중복 생성 거부, 오래된 기기 ID의 삭제 거부와 로컬 삭제 후 키 부재를 확인했다. Safari·Firefox·모바일·브라우저 완전 종료/재시작·저장소 거부·실제 두 기기 검증은 아직 남아 있다.
- 이후 키 감싸기 외피로 바꾼 버전은 웹 테스트 18개·타입 검사·lint·웹 빌드와 브라우저 검사 코드의 타입 검사·번들링까지 통과했다. 이번 실행 환경은 localhost listen을 `EPERM`으로 거부하고 Chrome의 로컬 검사 파일 열기도 승인 정책으로 차단해 새 외피의 브라우저 재검증을 완료하지 못했다. 전체 `pnpm check`의 relay 테스트 9개도 동일한 listen 제한으로 초기화에서 실패했다. 위 Chrome 성공 기록은 변경 전의 직접 HPKE 실험에 대한 것이며 새 외피의 브라우저 통과 증거로 사용하지 않는다.
- 같은 날 사용자가 현재 워크트리의 일반 터미널에서 `pnpm check`를 실행해 전체 통과했다고 확인했다. 전체 자동 검증은 사용자 실행 결과로 통과 처리한다. 새 외피의 브라우저 재검증은 이 명령에 포함되지 않으므로 별도로 남아 있다.

브라우저 검사는 `pnpm --filter @envhandoff/web dev --host 127.0.0.1`로 개발 서버를 띄운 뒤, 격리된 브라우저에서 아래 순서로 실행한다. 테스트 파일은 제품 빌드에 포함하지 않으며 `pnpm check`만으로 이 검사를 실행했다고 간주하지 않는다.

```js
// 개발 서버 페이지의 콘솔에서 실행
await (await import('/tests/team-crypto.browser.ts')).prepare()
// 페이지를 실제로 새로고침한 뒤 실행
await (await import('/tests/team-crypto.browser.ts')).verify()
```

성공하면 테스트 계정의 기기 키와 전용 검사 DB를 삭제한다. 실패 시에는 해당 격리 프로필의 테스트 데이터를 정리하고 다시 실행한다. 보관 방식의 근거는 [MDN의 CryptoKey 저장 설명](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto#storing_keys), [트랜잭션 완료 확인](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction), [HPKE의 발신 키 계약](https://dajiaji.github.io/hpke-js/docs/interfaces/SenderContextParams.html)이다.

팀 외피의 바이트 형식과 키 감싸기는 [팀 전달 외피 v1](team-envelope-v1.md)로 정리하고 기존 `createBundle`/`openBundle`의 파일 경로·원본 바이트 검증에 연결했다. 반환값은 감싼 키와 암호문 바이트뿐이다.

이어서 [기기 신뢰 v1](device-trust-v1.md)의 ECDH 소유 도전·ES256 서명, 최초 등록·추가 승인·회수·모든 기기 분실 복구, SQLite의 영속 일회성 소비를 구현했다. `apps/api` 테스트 4개는 실제 DB 재열기·동시 처리·만료·잘못된 계정/세션/키·회수 경쟁·한도·기록 정리를 포함한다. 웹 18개와 합계 22개 테스트, 전체 타입 검사·lint, 웹 빌드, 갱신한 브라우저 검사 코드의 타입 검사·번들링이 통과했다. 새 서명 키와 상대 지문 저장의 실제 브라우저 검사는 도구의 승인 제한으로 실행하지 못했다. 앞서 사용자가 확인한 전체 `pnpm check` 통과는 이번 기기 증명 변경 전 기록이다.

GitHub OAuth 로그인·SQLite 서버 세션·Origin/CSRF·로그아웃과 `/pro`의 로그인 확인 화면을 추가했다. [개발 실행과 보안 범위](../apps/api/README.md)에 등록 주소·환경 변수·수동 검사 순서를 정리했다. OAuth/세션 테스트 5개는 재시작·세션 교체·계정 ID 결합·만료·CSRF·동시 callback·로그아웃 경쟁·공급자 오류를 검사한다. 기존 기기 4개와 웹 18개를 합쳐 27개 테스트가 통과했다. 포트 listen과 브라우저 새 페이지가 실행 환경에서 거부되어 실제 GitHub 로그인은 아직 미검증이다.

2026-09-28 사용자가 개발용 OAuth 설정을 저장한 뒤 로컬 `/pro`에서 실제 GitHub 로그인과 계정 이름 표시 성공을 확인했다. 이어서 새로고침 후 로그인 유지와 한 탭의 로그아웃이 다른 탭에도 반영되는 것을 확인했다. 위 에이전트 실행 제한과 별개인 사용자 수동 검증 기록이다. 서버 재시작 후 세션 유지와 운영 HTTPS 쿠키 동작은 아직 확인 전이다.

조직 개설 초대·멤버 초대 수락, Owner/Member 관리 경계, 멤버 제외/본인 탈퇴, 기본 팀 소속과 베타 활성 상태 검사를 구현했다. 운영자 CLI에서만 계정에 묶인 개설 초대를 발급·취소하며 `/pro`에서 수락·조직 전환·멤버 초대/취소/제외를 진행한다. GitHub 로그인 이름은 발급 시 숫자 계정 ID로 확정한다. 만료·취소·다른 계정·초대자 자격 상실·중복 수락·탈퇴 후 과거 초대 재사용·20명 한도를 검사한다. API 14개와 웹 19개, 합계 33개 테스트와 전체 타입 검사·lint·웹 빌드가 통과했다. 새 조직 화면과 실제 두 계정의 초대 흐름은 브라우저 도구 승인 제한으로 미검증이다. [실행 및 수동 검사 순서](../apps/api/README.md#워크스페이스-개설과-멤버-초대)에 기록했다.

후속 사용자 화면으로 실제 개설 초대 수락·워크스페이스·Owner·멤버 초대 폼 표시를 확인했다. 사용자는 추가 GitHub 계정이 없어 Member 검증을 코드로 진행하도록 요청했다. 모의 계정의 독립된 세션으로 초대 발급/수락/재수락과 Member의 초대 발급·취소·타인 제외 API 거부, Owner의 취소/제외, 제외 후 접근/과거 초대 재사용 거부, 본인 탈퇴를 검사했다. API 테스트 15개·타입 검사·lint가 통과했다. Member 화면의 관리 버튼 조건은 코드로 검토했으며 실제 두 계정의 OAuth/브라우저 동작을 실행한 것으로 간주하지 않는다.

팀·프로젝트·환경 생성/이름 변경/삭제, 팀 소속과 프로젝트 연결, 독립된 환경별 받기·보내기·외부 공유 권한의 API와 `/pro` 화면을 구현했다. 현재 조직 자격·팀 경로·명시적 권한을 함께 검사하고 Owner도 파일 권한은 기본 거부한다. 복수 팀 중 다른 경로가 남으면 권한을 유지하며, 조직 탈퇴 후 재가입은 과거 권한을 되살리지 않는다. 기본 팀은 기존 ID·소속을 보존해 한 번만 이관하고 삭제는 막는다. 팀 삭제는 초대를 취소하며 프로젝트/환경 삭제는 하위 권한을 함께 정리한다. 모의 계정으로 조직 경계·Owner/Member 관리 경계·독립 권한·중지 계정·삭제·이관을 검증했다. 새 화면의 실제 브라우저 검증은 승인 제한으로 남아 있다.

이 단계에서 API 20개와 웹 19개, 합계 39개 테스트와 전체 타입 검사·lint·웹 빌드가 통과했다. 전체 `pnpm check`는 다시 실행하지 않았고, listen 제한이 있는 relay 테스트와 실제 브라우저 검사는 이 결과에 포함하지 않는다.

사용자 요청으로 로컬 개발 SQLite의 `test` 워크스페이스·팀·소속·초대를 삭제하고 계정·세션은 유지했다. 로컬 개발 DB는 재시작해도 유지되며 자동 테스트용 메모리/임시 DB와 분리돼 있다. 일반 사용자용 조직 삭제 API를 공개한 것은 아니다.

민감 작업용 최근 재인증과 기기 관리 HTTP·화면 연결을 완료했다(아래 후속 기록). 파일 요청 생성·승인·거절·취소와 요청에 대한 권한/기기 회수의 연쇄 종료를 연결했다. 암호화 업로드·수신·ACK와 전달 회수도 아래 후속 단계에서 연결했다. GitHub OAuth의 계정 선택은 자격 증명 재확인을 보장하지 않으므로 callback 시각을 최근 재인증으로 인정하지 않는다. Owner 이전·승격·강등은 아직 공개하지 않는다. 전달별 다운로드 소유 증명과 멤버 제외/기기 회수/유효 환경 권한 상실/프로젝트·환경 삭제의 요청·전달 종료를 DB 거래에 연결했다. 운영 저장소·백업/복원 차단은 남아 있다. 권한 재부여로 과거 회수된 전달을 부활시키지 않는다. 실제 브라우저·기기 및 보안 검토 조건은 그대로 유지한다.


### PostgreSQL 선택 — 2026-09-28

사용자가 운영 DB로 PostgreSQL, 개발 환경으로 로컬 Docker를 선택했다. SQLite 런타임을 제거하고 API·운영자 CLI·기기 저장소와 자동 테스트를 PostgreSQL로 전환한다. 개발/테스트 DB는 분리하고, 기존 SQLite 파일은 보존하되 데이터를 자동 복사하지 않는다. 새 DB 로그인과 별도 워크스페이스 개설이 필요하다. 운영 호스팅과 배포·백업/복원 검증은 아직 남아 있다. 실행 방법과 전환 검증 상태는 [API README](../apps/api/README.md#postgresql-전환과-검증)를 기준으로 한다.

후속 세션에서 OrbStack PostgreSQL 기동·스키마 적용과 전체 `pnpm check`를 완료했다. 실제 PostgreSQL API 21개·웹 19개·relay 9개, 총 49개 테스트와 타입 검사·lint·빌드가 통과했다. 기존 API 개발 서버도 정상 기동했으며 이전의 Docker·로컬 네트워크 접근 제한은 재현되지 않았다. PostgreSQL 전환 후 실제 OAuth·브라우저 검증은 별도로 남아 있다.


### 재인증·기기 관리 연결 — 2026-09-28

사용자는 패스키를 기본으로 선택하고 인증 앱도 추가할 수 있도록 요청했다. `/pro`에서 두 수단의 등록·삭제·15분 재인증과 현재 브라우저 기기 등록·지문 대조 승인·회수·모든 기기 분실 복구를 연결했다. 첫 수단은 로그인 후 15분 안에 설정하고 이후 추가·삭제에는 기존 수단 재인증을 요구한다. 마지막 수단 삭제나 분실 후 무인 우회 초기화는 제공하지 않는다. 인증 앱 키는 별도 서버 키로 암호화하고 QR은 클라이언트에서만 만든다. 동시 코드 재사용, 다른 출처/세션, 만료, 소속 상실·로그아웃 후 기기 증명 완료를 거부한다. 상세 정책·실행·검증은 [API README](../apps/api/README.md#패스키인증-앱과-기기-관리)를 따른다.

API 26개·웹 19개·relay 9개, 총 54개 테스트와 타입 검사·lint·빌드를 통과했다. 격리된 Chrome에서 테스트 DB의 인증 앱 등록·재인증과 기기 등록/회수·390px 레이아웃을 확인했다. 실제 Touch ID/보안키·인증 앱 스캔·두 물리 기기와 운영 환경 검증은 아직 남아 있다. 파일 전달과 연쇄 회수, Owner 이전·조직 삭제는 이번 구현 범위에 포함하지 않았다.

### 요청함 연결 — 2026-09-28

요청 생성·승인·거절·취소, 생성 후 7일 만료와 요청함을 연결했다. 요청자는 받기 권한과 자기 활성 수신 기기가 필요하고 지정 송신자는 보내기 권한이 있어야 한다. 현재 Owner의 관리 조회·취소는 파일 권한과 분리한다. 작업 ID로 중복 생성·승인을 방지하며 취소·권한 재부여로 종료된 요청을 복원하지 않는다. 팀·환경 권한·멤버 제외·프로젝트/환경 삭제·수신 기기 회수·계정 중지와 요청 취소를 같은 DB 거래에서 확정한다. 종료 조회는 최소 식별자와 상태·시각으로 제한한다. 상세 API와 한도는 [API README](../apps/api/README.md#팀원-파일-요청)를 따른다. 업로드·수신·ACK 및 전달에 대한 연쇄 회수는 아래 후속 단계에서 연결했다.


### 팀원 암호화 전달 — 2026-09-28 세션 복구 후

요청 승인 후 업로드 예약·팀 외피 암호화·송신 기기 증명·객체 저장·조건부 확정, 지정 수신 기기의 다운로드·전체 인증·ACK·재다운로드와 전달 회수를 연결했다. 업로드 중 취소와 권한 상실이 확정되면 뒤늦은 업로드를 거부하고, 권한 재부여로 회수된 전달을 복원하지 않는다. 요청 기한과 업로드 확정 후 보관 기한은 별개다. 저장소·API·한도는 [API README](../apps/api/README.md#팀원-파일-업로드수신ack)에 기록한다.

`pnpm check`의 API 37개·웹 19개·relay 9개, 총 65개 및 타입 검사·lint·빌드가 통과했다. 격리된 Chrome 두 컨텍스트와 PostgreSQL 테스트 계정에서 실제 화면의 지문 대조·암호화 업로드·송신자 로그아웃 후 수신·ACK·재다운로드·회수 후 410을 확인했다. 원본 다운로드 Blob의 34바이트, BOM·CRLF와 송신 화면 390px 가로 넘침 없음을 확인했다. 지문 불일치 오류가 영어로 노출되던 문구를 한국어로 수정하고 브라우저에서 다시 확인했다.

사용자 요청에 따라 [QA 기록](qa.md)을 Markdown으로 저장했다. 확인한 범위만 PASS로 표시하고 미구현·에이전트 검증 대기·실제 장치의 최종 확인을 구분한다. 외부 공유, 장애 주입·삭제 실패·백업 복원·운영 HTTPS와 지원 브라우저 검증은 남아 있다.

### 외부 공유·장애 주입 — 병렬 작업 후

비회원 외부 공유 API·화면, 코드와 링크 분리·미리보기·복호화 후 ACK·토큰 재발급·Owner 회수, 로그인 후 내부 상세 복귀를 연결했다. 팀 전달과 저장·생성·다운로드 한도를 합산하고 공유 ID 충돌과 비정규 경로 제한 우회를 차단했다. 업로드 응답 유실·SIGKILL·권한/기기 회수 경쟁·삭제 실패·부분 다운로드 중단을 검사했다. 브라우저에서는 합성 파일의 원본 바이트, 잘못된 코드 거부·ACK 없음, 새 링크에서 기존 코드 사용, Owner 경계와 다중 탭의 상태 정리를 확인했다.

복원된 전달을 닫는 운영자 명령과 [운영 절차](operations.md)를 추가했다. API를 중지한 상태에서 차단하고 오래된 객체 볼륨을 폐기하는 절차이며 운영 인프라를 구성하거나 실제 백업 복원 훈련을 완료한 것은 아니다. 최종 검사 수와 남은 범위는 [QA 기록](qa.md)을 기준으로 한다.

병렬 구현 최종 `pnpm check`: API 69개·웹 22개·relay 9개, 총 100개 및 전체 타입 검사·lint·빌드 PASS. 운영 배포와 실제 장치 검증은 이 결과에 포함하지 않는다.

### Pro 제품 화면과 관리 기능 — 2026-09-28

기존 한 화면을 시작·요청함·프로젝트·외부 공유·팀 관리·내 설정으로 분리하고 목록/상세/생성 경로, 프로젝트 환경에서 작업 시작, 뒤로 가기·로그인 복귀와 작업 손실 확인을 연결했다. Owner 변경·이전·탈퇴의 재인증과 마지막 활성 Owner 보호, 조직 삭제의 원자적 접근 종료를 구현했다. 기존 코드의 일시적인 세션 조회 실패로 메모리 코드가 사라지던 문제도 수정했다.

전체 `pnpm check`는 API 73개·웹 24개·relay 9개, 총 106개 PASS. 이 결과는 제품 화면의 로컬 구현과 검사 결과이며 v3.0 출시 완료 선언이 아니다. 실제 OAuth 왕복·실기기·지원 브라우저와 운영 환경 검증은 남아 있다. 수용 검사별 범위는 [QA 기록](qa.md)을 따른다.

### 남은 구현 병렬 작업 — 2026-09-28

계정 삭제 API와 내 설정 화면, DB 백업과 분리한 영구 삭제대장, 시작·요청·재해 복원 시 삭제 우선 적용을 연결했다. 마지막 활성 Owner는 이전이나 조직 삭제가 필요하고 삭제대장이 없거나 손상되면 삭제 성공을 반환하지 않는다. 같은 GitHub 계정의 새 가입은 새 내부 ID로 가능하며 이전 계정의 관계는 되살리지 않는다.

운영자 전용 `management-recovery`는 사전에 등록한 연락 검증 참조와 새 사건 참조, GitHub 숫자 ID·기존 Owner 목록을 대조해 관리 역할만 변경한다. 기본 조회에도 메타데이터 열람 감사를 기록하며 실제 역할·세션·초대 변경에는 `--apply`가 필요하다. 기존 파일 권한·기기 키·신뢰는 복구하지 않는다. 1절의 제외 범위도 파일 키 복구로 명확히 했다.

브라우저 등록 해제는 서버 회수 후 로컬 키와 상대 지문 기록을 함께 삭제한다. 오프라인 로컬 삭제는 서버 회수 미완료임을 표시한다. 신규 전달 접수 중단은 `PRO_ACCEPT_NEW_TRANSFERS=false`로 제어하며 기존 전달의 다운로드·ACK·회수·기한과 멱등 결과 조회는 유지한다. 운영 환경 설정을 실제로 변경한 작업은 아니다.

전송 화면에는 진행률·업로드 취소, 탭 복귀 시 권한·목록 갱신, 기기 설정/새 요청 동선, 한도 재시도 조건과 메타데이터·ACK 의미를 보완했다. 이번 변경의 브라우저·실기기 QA는 사용자 요청에 따라 구현 이후로 미뤘다. 자동 검사와 남은 범위는 [QA 기록](qa.md)에 누적한다.

### 추가 누락 보완 — 2026-09-28

위 완료 판단 후 재대조에서 다운로드 거부 감사, 복원 미리보기 열람 감사, 24시간 삭제 지연 감지, 긴급 계정 중지 CLI의 네 가지 누락을 확인했다. 자동 검사 통과를 명세 전체 구현 완료로 간주했던 판단을 정정한다.

다운로드 거부는 실제 확정 객체에 최소 기록을 남기고 요청 거래 롤백 후에도 별도 저장한다. 반복 공격에 의한 기록 폭주를 막기 위해 대상·사건 종류당 분당 첫 건만 기록한다. 복원 도구는 미리보기·적용·재실행을 감사하며, 미리보기는 기존 전달 상태를 보존한다.

`deletion-health`는 1시간 방치 업로드와 24시간 삭제 지연을 읽기 전용으로 집계하며, API의 기존 분 단위 정리에도 같은 지연 감지와 JSON 경보를 연결했다. `disable-account`는 내부 UUID와 GitHub 숫자 ID를 대조하고 기본 조회, 명시적 적용으로 동작한다. 세션·초대·관련 전달 차단은 기존 내부 함수와 같은 거래를 사용한다. 명령·감사 범위는 [운영 절차](operations.md)를 따른다.

네 항목의 구현과 실제 외부 감시 연결·운영 실행·브라우저 QA는 구분한다. 운영 계정 중지나 복원 명령을 실제 데이터에 실행하지 않았고 외부 알림도 발송하지 않았다.

보완 후 `pnpm check`: API 101개·웹 27개·relay 9개, 총 137개와 타입·lint·빌드가 통과했다. 통과 범위는 [QA 기록](qa.md)을 따른다.


### 참여 화면과 탐색 보완 (2026-09-29)

사용자 화면은 ‘워크스페이스 초대 링크’와 ‘베타 참여 코드’를 구분한다. `/pro`의 **워크스페이스 참여**에서 초대 링크를 수락하고, 베타 코드는 별도 활성화 화면으로 안내한다. 초대 발급은 **멤버 · 팀 → 워크스페이스에 멤버 초대**에서 진행한다. 워크스페이스 전환 시 현재 메뉴를 유지하고, 참여 화면을 열어도 선택된 워크스페이스를 유지한다. 새 초대 링크는 이전 OAuth 복귀 경로보다 우선한다.
