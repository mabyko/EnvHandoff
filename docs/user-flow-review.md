# EnvHandoff 사용자 흐름 검토

검토일: 2026-10-12. 신규 팀원의 첫 수신, 기존 팀원의 설정 교환, 계정 없는 공유를 병렬 검토했다. 최초 검토는 개선 제안이며 구현·검증 결과는 아래 후속 구현과 구분한다. 실제 사용자 관찰로 확인한 이탈 원인과 코드에서 확인한 동선 문제를 구분한다.

후속 구현: 같은 날 사용자 승인으로 기존 흐름 연결·오류 복구·배치 안내를 구현했다. 실제 동작은 [Pro 웹 설계](pro-web-design.md), [무료 웹 설계](web-design.md), [Pro 명세](pro-v3-spec.md)에 반영하며 검증 결과는 [QA 기록](qa.md)에 둔다. 아래 최초 검토의 제안 전체를 구현한 것은 아니다. 초대 자동 미리보기·파일 비교·CLI·자동 적용은 이번 범위에 포함하지 않는다.

## 판단

먼저 개선할 부분은 현재 단계·담당자·다음 행동과 화면 사이 복귀다. 이미 있는 단계 표시, 고급 설정 접기, 초대 종류 구분, 인증 후 다운로드, 현재 권한 재검사, 작업 손실 경고는 유지한다. 읽기 전용 파일 비교는 이 연결을 정돈한 다음 추가할 후보다.

근거 자료: [현재 웹 설계](pro-web-design.md), [권한·기기·전달 계약](pro-v3-spec.md), [경쟁 제품 조사](team-secrets-tools-research.md). 아래 제안의 목적은 필요한 보안 단계를 사용자의 작업 안에서 이해하고 이어갈 수 있게 하는 것이다.

## 1. 신규 팀원의 첫 수신

현재 초대 수락은 요청함으로 이동한다. 그 뒤 기기 준비·접근 가능한 환경·받기 권한을 확인해야 한다. 기기 등록이 필요한 경우 요청 작성 화면에서 설정으로 이동하지만, 요청으로 복귀하는 경로와 선택 유지가 없다. 이것은 코드에서 확인한 구조이며 실제 이탈 빈도는 아직 측정하지 않았다.

근거: [수락 후 이동](../apps/web/src/components/ProOrganizations.tsx#L203), [요청 생성과 기기 검사](../apps/web/src/components/ProRequests.tsx#L139), [기기 설정](../apps/web/src/components/ProSecurity.tsx#L31), [프로젝트 빈 상태](../apps/web/src/components/ProCatalog.tsx#L124).

제안 흐름:

1. 초대 링크를 열고 GitHub 로그인 → 초대 내용을 조회 → 대상 계정·워크스페이스·팀을 확인하고 명시적으로 참여한다. 유효한 링크의 내용 조회는 자동화할 수 있어도 수락은 자동화하지 않는다.
2. 참여 완료 화면에서 다음 행동을 정한다. 받을 수 있는 환경이 있으면 프로젝트 선택, 진행 중 요청이 있으면 요청 열기, 필요한 환경·권한이 없으면 Owner에게 보낼 안내를 복사한다.
3. 환경·송신자를 고르는 화면에서 현재 브라우저 준비 상태를 먼저 확인한다. 등록 필요 또는 추가 기기 승인 대기를 구분한다.
4. 필요한 경우 기존 기기 설정 화면으로 이동하고, 준비 후 작성하던 요청으로 돌아온다. 환경·멤버 선택과 복귀 경로는 해당 작업 메모리에 유지하며 평문 파일·키·공유 코드는 저장하지 않는다. 설정 중 재인증·로그아웃·권한 변경 시 초안을 재검사한다.
5. 요청 → 승인·파일 준비 대기 → 상대 기기 신뢰 확인 → 파일 열기 → 다운로드·배치 안내로 이어간다.

권한 부족은 프로젝트 연결·환경 등록·받기 권한·보내기 가능한 멤버 부재를 현재 서버가 공개한 범위 안에서 구분한다. 필요한 워크스페이스·프로젝트·환경과 작업을 담은 안내 복사를 제공하되 자동 메시지 발송이나 권한 부여는 하지 않는다.

첫 상대 확인에는 사람·기기 표시명을 앞에 두고 내부 ID와 실제 공개키 지문은 대조 가능한 상세에 유지한다. 자기 지문 복사와 별도 경로 대조 안내를 전달 화면에 모을 수 있다. 표시명은 신원·키 인증의 근거가 아니다. [현재 상대 확인](../apps/web/src/components/ProTransfer.tsx#L154), [자기 지문 표시](../apps/web/src/components/ProSecurity.tsx#L189).

## 2. 기존 팀원의 설정 교환

현재도 요청 상세 하나에서 승인·송신·수신을 처리한다. 화면을 새로 쪼개기보다 지금 할 행동을 앞에 놓는 편이 작고 효과적인 변경이다.

요청함은 내가 처리할 일·상대를 기다리는 일·종료된 일을 구분하고, 기본 카드 행동을 승인하기·파일 준비·파일 받기·결과 보기로 바꾼다. 조직 Owner의 관리 조회를 파일 수신 권한으로 표시하지 않는다. [요청함](../apps/web/src/components/ProRequests.tsx#L156).

상세는 환경·상대 → 현재 단계·담당자 → 주 행동 하나 → 결과·복구 → 식별 정보·위험한 작업 순서로 구성한다.

- 승인 대기: 지정 송신자는 승인 또는 거절한다. 수신자는 요청 링크 복사와 상태 확인을 제공받는다.
- 승인 후 파일 준비: 송신자는 현재 상대 기기를 조회하고 파일을 선택한다. 이미 고정한 신뢰가 유효하면 재사용하지만 새 키를 자동 신뢰하지 않는다.
- 업로드 중: 업로드 중단은 가까이 두고 요청 전체 종료는 분리한다. 결과가 불명확하면 결과 확인을 먼저 제공한다.
- 전달 이용 가능: 지정 수신자와 원래 기기는 파일 받기를 제공받는다. 송신자는 상세 링크 전달과 결과 확인을 제공받는다.
- 파일 열기 성공: 다운로드를 계속 제공한다. 수신 확인 보고만 실패하면 열린 파일을 유지하고 보고 재시도를 제공한다.
- 만료·회수·기기 변경: 현재 권한과 공개 가능한 정보로 재요청 경로를 정한다. 종료된 상세에서 서버가 숨긴 과거 환경·송신자 정보를 항상 복원할 수 있다고 약속하지 않는다.

근거: [수동 기기 조회와 신뢰 재사용](../apps/web/src/components/ProTransfer.tsx#L45), [상대 ID 표시](../apps/web/src/components/ProTransfer.tsx#L154), [요청 취소·회수](../apps/web/src/components/ProRequests.tsx#L170), [업로드 시도 취소](../apps/web/src/components/ProTransfer.tsx#L182), [수신 확인 실패](../apps/web/src/components/ProTransfer.tsx#L145).

승인 대기·송신 준비·전달 이용 가능은 작업 단계이며 수신 확인은 별도 기록이다. 과거 수신 확인과 현재 만료·회수는 함께 표시할 수 있다. 수신 확인은 로컬 저장·프로젝트 적용의 증거가 아니다.

## 3. 계정 없는 공유와 Pro 외부 수신

무료 공유는 이미 2단계 표시와 기본 파일 공유, 접힌 옵션을 제공한다. 홈에 기능 선택지를 더 늘리기보다 파일 선택 뒤 전달 방식이 드러나도록 한다. 파일로 건네기와 지금 함께 접속해 전달하기를 구분하고, 표시명·환경 이름은 보조 설정에 유지한다. [현재 공유 설정](../apps/web/src/components/SendFlow.tsx#L325).

송신 흐름은 파일 선택·배치 경로 확인 → 전달 방식 → 암호화 → 파일 또는 링크 전달 → 코드는 별도 경로로 전달이다. Pro 외부 공유 생성 후에는 링크·코드 전달을 앞에 놓고 재발급·회수는 관리 영역에 둔다. 링크 재발급은 코드 복구나 만료 연장이 아니며 이전 링크를 무효화한다. [외부 공유 생성](../apps/web/src/components/ProShares.tsx#L102), [공유 관리](../apps/web/src/components/ProShares.tsx#L208).

무료 화면은 메모리 상태로만 이동하고 브라우저 방문 기록을 추가하지 않는다. 기본 뒤로 가기를 앱의 이동과 연결하는 개선을 검토한다. 뒤로 이동 시 작업 손실 확인을 유지하고, 키·코드·파일을 URL·방문 기록에 넣지 않는다. [현재 이동](../apps/web/src/App.tsx#L56).

수신은 공유 파일 또는 링크 → 필요한 연결 확인과 송신 승인 → 별도 코드 → 인증된 목록 → 다운로드·배치 안내로 이어진다. 브라우저는 파일 저장의 성공이나 적용 결과를 알 수 없으므로 다운로드 요청과 프로젝트 적용을 구분한다.

특히 apps/api/.env와 apps/web/.env는 다운로드에서 둘 다 .env라는 끝 파일명을 사용한다. 각 파일의 원래 배치 경로와 브라우저 저장 결과를 연결할 안내가 필요하다. 임의로 확장자·원본 이름을 바꾸거나 자동 적용하지 않는다. 파일별 경로 복사와 배치 안내부터 개선하고, 기존 파일 비교는 후속 기능으로 연결한다. [공통 수신·다운로드](../apps/web/src/components/ReceiveFlow.tsx#L241).

Pro 외부 수신은 열기 성공 후 코드를 지운다. ACK 실패 때 파일을 다시 열라는 안내는 코드 재입력·재다운로드를 유발할 수 있다. 열린 파일을 유지하고 ACK만 재시도하는 행동으로 분리한다. 재시도 때도 현재 공유 상태·권한 검사는 유지한다. [현재 외부 수신](../apps/web/src/components/ExternalReceive.tsx#L40).

무료 일반 파일에는 서버 보관 만료가 없다. Relay의 세션·열기 대기 시간과 Pro 외부 공유의 이용 기한·삭제 기한은 서로 다른 정책이다. 하나의 만료·복구 설명으로 합치지 않는다.

## 구현 우선순위와 완료 기준

1. 요청함·상세의 상태별 담당자와 주 행동, 요청 작성의 기기 준비 상태와 설정 후 복귀, 빈 상태의 구체적 해결 안내를 먼저 연결한다.
2. 무료 공유의 방식 선택, Pro 외부 공유의 링크·코드 전달 영역, 다운로드 후 경로 안내, ACK 단독 재시도와 취소 문구를 다듬는다.
3. 파일 비교·예시 키 누락 안내를 추가한다. CLI·자동 적용·지속 보관은 기존 후속 제품 범위와 따로 다룬다.

각 변경은 기존 요청·전달 상태와 권한 계약에서 가능한 행동만 표시해야 한다. 파일·키의 영구 저장이나 새로운 알림 서버는 필요하지 않다. 현재 상태 자동 조회를 도입하더라도 기기 등록·초대 수락·상대 신뢰·송신 승인을 자동 완료하지 않는다.

검증은 신규 Member/Owner, 첫 기기/추가 승인 대기/기존 신뢰/키 변경, 현재 권한 상실, 원래 기기 불일치, 업로드 결과 불명, ACK만 실패, 취소·뒤로가기, 같은 끝 파일명의 서로 다른 배치 경로를 포함한다. 실제 OAuth와 두 계정·두 기기 검증을 코드 검사로 대체하지 않는다.

## 이번 검토의 검증 범위

코드·명세를 확인했고 로컬 브라우저에서 홈 → 무료 보내기, 접힌 공유 설정 열기, 홈 → 무료 받기의 빈 화면을 살폈다. 1280px과 375px에서 해당 화면을 확인했고 홈·무료 작업의 URL이 /로 유지됨을 관찰했다. 이를 전체 모바일·접근성·브라우저 QA 완료로 해석하지 않는다.

최초 검토에서는 앱 코드를 수정하지 않았고 실제 OAuth 왕복·Pro 서버 연결·두 계정/두 기기 전송·암호화 전체 왕복·실사용 관찰·지원 브라우저 검증은 하지 않았다. 제안 우선순위는 현재 근거에 따른 판단이며 실제 사용자 작업 관찰로 조정해야 한다. 이후 구현·검증은 위의 QA 기록과 구분한다.
