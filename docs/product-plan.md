# EnvHandoff 제품·구현 설계 초안

작성일: 2026-09-08. 갱신일: 2026-09-11. 상태: 웹 0.0.1의 일반 파일 공유와 로컬 실시간 relay 구현. 실제 배포와 데스크톱 앱은 후속 작업이다. 사용자와 합의한 제품 방향과 아래의 제안값을 구분한다.

웹부터 구현한다. 현재 구현 범위와 모노레포 구성은 [웹 우선 구현 설계](web-design.md), 후속 Tauri 앱의 화면·이동·상태는 [데스크톱 화면 설계](app-design.md), 공통 용어는 [CONTEXT.md](../CONTEXT.md)에 정리한다.

## 1. 제품 목표와 범위

프로젝트 코드를 받은 개발자가 Git에 없는 설정 파일도 받아서 자기 프로젝트에 적용할 수 있게 한다. 공유 단위는 개별 키가 아니라 파일이며, 여러 파일은 하나의 공유 묶음으로 전달한다.

합의한 순서는 일반 공유 → 저장 없는 실시간 relay → 팀 초대·요청과 임시 보관 → 유료 클라우드 보관이다. 초기 대상은 `.env`이며, 같은 방식으로 개발 설정 파일을 다룬다. Firebase·Vercel 관련 파일도 사용자가 직접 선택할 수 있다. 파일 이름만으로 비밀 파일이라고 판단하거나 특정 제품의 모든 설정을 자동 수집하지 않는다.

첫 버전의 중심 시나리오: 기존 팀원이 개발 설정을 보내고, 신규 팀원이 원본을 손상시키지 않고 가져온다. 개발 환경을 대상으로 시작하며 운영 비밀값의 조직적 관리는 초기 검증 범위 밖이다. 그렇다고 파일 보호 수준을 낮추지는 않는다.

2026-09-11 합의: v2.0까지는 서로 아는 사람끼리 일회성으로 전달하는 흐름에 맞춘다. 암호화한 파일을 직접 공유하거나 연결 링크로 실시간 전송할 수 있다. 받는 사람은 기존 개인 대화에서 확인하며, 계정·이메일 인증과 서비스의 자동 메일 발송은 이 범위에 포함하지 않는다.

같은 날 웹 우선 구현을 선택했다. 웹 첫 출시는 암호화 공유·수신·다운로드에 집중하고, 프로젝트 폴더의 비교·직접 적용·복구는 후속 데스크톱 범위로 둔다. 선택한 D의 시각적 방향은 유지하되, 웹에서 지원하는 행동에 맞춰 화면 흐름을 조정한다.

## 2. 단계별 출시 범위

제품의 큰 기능 확장에 맞춰 1.0 → 2.0 → 3.0 → 4.0 순서로 구현한다. 첫 배포 목표는 웹에서 1.0 일반 공유를 완성하고 2.0 실시간 relay까지 포함하는 것이다. 데스크톱 추가 시점은 이 기능 단계와 별도로 관리하며, Tauri 앱 개발은 웹 이후에 시작한다. 아래 단계명과 공유 파일 형식 버전은 별도로 관리한다. 웹의 시작 구현 버전은 0.0.1로 정했으며 루트와 workspace package.json에 반영했다.

| 단계 | 사용자에게 제공하는 것 | 서버가 맡는 것 | 완료 기준 |
|---|---|---|---|
| v1.0 일반 공유 | 웹에서 파일 선택, 암호화 내보내기, 코드로 열기, 내용 확인·다운로드 | 웹 정적 파일 제공. 사용자 파일을 처리하는 서버 기능 없음 | 두 기기에서 공유 파일을 전달하고 원본 바이트 그대로 복호화·다운로드 |
| v2.0 실시간 relay | 일반 파일 공유에 더해 두 앱을 일회성 세션으로 연결해 암호화 파일 바로 전달 | 연결·세션 관리, 암호문 실시간 중계. 파일 보관 없음 | 상대 확인과 송신자 승인, 두 앱 동시 접속 전송, 세션 접근 제한, 중단·재전송·변조 거부 검증 |
| v3.0 팀 공유·임시 보관 | 팀·프로젝트 초대, 환경별 접근, 요청마다 보유자가 승인·전송, 전달 상태 | 계정·권한·요청, 암호문 임시 보관 | 승인된 수신자만 복호화, 재시도·만료·취소·권한 회수 검증 |
| v4.0 유료 클라우드 보관 | 권한자가 게시된 파일을 필요할 때 직접 수신, 버전 보관·복원, 접근 기록, 구독 | 암호문 지속 보관과 버전·과금 관리 | 기기 교체·팀 복구·퇴사·삭제까지 운영 검증 |

v2.0의 실시간 전송은 전송 중 양쪽 앱이 접속해 있어야 한다. 연결이 끊기면 전송을 실패로 처리하고 다시 연결해 처음부터 보낸다. 파일로 공유할 때는 이 조건이 없으며 받는 사람이 나중에 파일을 열어도 된다. 계정·팀·초대·요청함은 v3.0에서 추가하고, 이메일 인증·발송 여부는 그 단계의 인증 방식과 함께 결정한다.

24시간 임시 보관은 v3.0 제안값이다. 서버가 전달 완료 또는 만료 후 삭제한다. 수신은 ACK 이전까지 재시도 가능하며, 다운로드 시작만으로 삭제하지 않는다. 만료는 서버 재다운로드를 제한할 뿐 이미 받은 사본을 없애지 않는다.

v3.0은 업로드 후 송신자가 오프라인인 동안에도 수신할 수 있다. v4.0에서는 게시된 파일을 지속 보관하므로 다운로드할 때마다 보유자에게 새로 전송을 요청할 필요가 없다. 접근 권한 확인은 두 단계 모두 유지한다.

v1.0에서는 계정, 팀 관리, 자동 동기화, 파일 감시, 키별 편집·병합, 서비스 API 연결, 결제, 버전 이력을 만들지 않는다. 내보내기는 그 시점의 스냅샷이다. 나중에 원본이 바뀌어도 이미 공유한 파일은 바뀌지 않는다.

## 3. 후속 데스크톱의 v1.0 사용자 흐름

웹의 현재 흐름은 [웹 우선 구현 설계](web-design.md)를 따른다. 아래의 프로젝트 폴더 선택·Git 검사·직접 적용·백업·복구는 후속 Tauri 앱에서 제공할 동작이며, 웹 첫 출시의 완료 조건으로 사용하지 않는다.

### 보내기

1. 시작 화면의 `파일 보내기`를 누르면 `프로젝트 폴더 선택`과 최근 폴더를 보여준다. OS 폴더 선택창에서 기존 폴더 하나를 고르거나 최근 폴더를 연다. 취소하면 기존 화면과 작업을 유지한다.
2. 선택한 폴더명·경로와 `폴더 변경`을 표시한다. 폴더 바로 아래의 `.env`, `.env.*` 일반 파일을 후보로 표시하고 사용자가 체크한다. 초기 체크는 비워 둔다. 다른 설정 파일은 OS 파일 선택창으로 직접 추가하며 프로젝트 밖 파일은 거부한다.
3. 상대 경로, 파일 크기, Git 추적·ignore 상태를 확인한다. 파일 내용은 기본적으로 숨긴다. ignore 상태를 확인할 수 없으면 추측하지 않고 표시한다.
4. 프로젝트 표시명과 환경 이름을 입력한다. 초기 환경 이름은 `development`를 제안하되 선택을 확인한다.
5. 앱이 공유할 때마다 새 키를 생성하고 `.envhandoff` 파일을 만든다. OS 공유 기능 또는 파일 저장으로 전달한다. 생성한 파일은 AirDrop, 기존 메신저·이메일의 첨부 등 사용자가 선택한 경로로 공유할 수 있다. 이메일에 직접 첨부해 보내는 동작은 서비스의 메일 발송이나 수신자 이메일 인증을 뜻하지 않는다.
6. 별도의 전달 화면에서 공유 코드를 복사한다. 파일과 코드를 한 번에 같은 메시지에 넣지 않는다. 다른 연락 수단이나 대면 전달을 안내한다.

공유 코드가 있는 사람은 해당 파일을 열 수 있다. v1.0과 v2.0에는 수신자 계정·이메일 확인, 이미 전달된 파일의 원격 회수, 코드 복구가 없다. 코드를 잃으면 원본에서 새로 내보낸다. 짧은 숫자 PIN이나 사용자가 정한 약한 비밀번호는 제공하지 않는다.

파일과 공유 코드를 별도로 전달하는 흐름을 1.0의 기본 방식으로 유지한다. 초기 가치는 기존에 흩어진 설정 파일을 수집·전달하고 각 경로에 배치하던 수고를 줄이는 데 둔다. 별도 코드 전달의 사용성을 먼저 입증해야 구현을 시작할 수 있다는 조건은 두지 않는다.

### 받기

1. `.envhandoff` 파일을 열고 공유 코드를 입력한다.
2. 크기 제한과 암호문 인증을 통과한 뒤에만 파일 목록을 읽는다. 손상·잘못된 코드·미지원 버전이면 파일을 쓰지 않는다.
3. 수신자가 적용할 로컬 프로젝트 폴더를 직접 고른다. 보낸 사람의 절대 경로나 표시명으로 자동 연결하지 않는다.
4. 각 파일을 `새 파일 / 동일 / 변경 / 적용 불가`로 표시한다. 동일 파일은 건너뛰고 변경 파일은 기본적으로 덮어쓰지 않는다.
5. 필요할 때 내용을 펼쳐 비교한다. 원본 바이트를 바꾸지 않는 미리보기이며, UTF-8로 표시할 수 없는 파일은 경로·크기와 교체 여부만 보여준다.
6. 사용자가 적용할 파일을 고르고 확인한다. 사전 검사와 암호화된 복구 백업을 완료한 뒤 적용한다.
7. 성공·건너뜀·실패한 경로를 표시한다. 적용 중 오류가 나면 추가 적용을 멈추고 이번 작업에서 바꾼 파일의 자동 복구를 시도한다. 복구 결과도 표시하고, 완료하지 못한 작업을 성공으로 보이지 않는다.

받은 파일을 실행하거나 셸에서 `source`하지 않는다. 앱은 내용을 배치하는 데까지만 책임진다. 개발 도구가 그 설정을 어떻게 사용하는지는 별개이며, 보내는 사람을 신뢰할 수 있어야 한다.

### 첫 화면 구성

D의 단계별 안내를 실제 앱의 기준으로 선택했다. 세부 화면은 [화면 흐름과 구현 설계](app-design.md)를 따른다.

- 시작: `파일 보내기`, `파일 가져오기`.
- 보내기: 프로젝트 폴더 선택 → 파일 선택 → 공유 방식 → 파일·코드 전달 또는 실시간 전송.
- 가져오기: 공유 파일·코드 확인 → 적용 폴더 선택 → 변경 확인 → 적용 결과.
- 복구: 적용 결과나 미완료 작업 안내에서 복구 확인과 파일별 결과로 이동.

후속 데스크톱 앱은 Tauri 2로 구현한다. macOS에서 먼저 개발하고 Windows 검증도 데스크톱 첫 출시에 포함하는 것을 목표로 한다. OS 공유 기능과 파일 열기 연결은 각 OS에서 검증한다.

## 4. 공유 파일 형식 v1

자체 암호 알고리즘을 만들지 않는다. 웹 0.0.1은 브라우저의 Web Crypto API를 사용하고, 후속 Rust 코어에서는 유지보수되는 암호 라이브러리 또는 플랫폼 구현을 선정한다. 구현 언어와 관계없이 같은 파일 규격과 테스트 벡터로 호환성을 검증한다. 정확한 바이트 규격은 [파일 형식 v1](bundle-format-v1.md)에 고정했다.

```text
공개 헤더: magic(10B) + formatVersion(2B) + nonce(12B), 전체를 AAD로 인증
암호화 영역: authenticated ciphertext + tag(16B)

복호화된 payload:
{
  "formatVersion": 1,
  "bundleId": "무작위 식별자",
  "projectLabel": "example-app",
  "environment": "development",
  "createdAt": "UTC timestamp",
  "files": [
    { "path": ".env", "contentBase64": "원본 바이트의 Base64" }
  ]
}
```

파일 내용은 key/value로 파싱하지 않는다. 주석, 빈 줄, 줄바꿈, 인코딩을 원본 바이트 그대로 보존한다. 작은 설정 파일이 대상이므로 압축·ZIP 추출 없이 하나의 UTF-8 JSON payload를 암호화한다.

- 암호 구성: AES-256-GCM, 내보내기마다 CSPRNG로 새 256비트 키와 96비트 nonce 생성, 128비트 인증 태그. 공개 헤더는 AAD로 인증한다. 구현에서는 라이브러리의 검증된 사용법을 따른다.
- 공유 코드는 키의 Base64url 표현이다. 로그, 명령행 인자, 분석 이벤트에 넣지 않는다. 내보내기 완료 후 앱 종료를 넘어 자동 보관하지 않는다.
- 프로젝트명, 환경명, 파일 경로, 생성 시각은 암호화 영역에만 둔다. 공개 헤더로 파일 버전을 판별하고 미지원 버전은 거부한다.
- bundleId와 생성 시각은 송신자가 작성하는 값이다. 발신자 인증, 최신 버전 증명 또는 접근 권한으로 사용하지 않는다.
- v1 제한: 원본 합계 10 MiB, 파일당 1 MiB, 최대 100개, 입력 패키지 최대 16 MiB. 읽기·복호화·파싱·Base64 디코딩 모두 제한을 적용한다.
- 헤더·직렬화·키 인코딩·경로·오류의 상호운용 규칙과 공개 벡터는 [파일 형식 v1](bundle-format-v1.md)을 기준으로 삼는다. 다운로드 파일명에도 프로젝트 표시명을 넣지 않는다.

v2.0의 실시간 relay는 v1 암호화 묶음을 전달하는 통로로 구현한다. 묶음을 전송용 조각으로 나누더라도 전체 수신과 인증을 마친 뒤에만 복호화된 파일을 처리한다. 세션 참여에 사용하는 토큰과 파일 복호화 키는 별개이며, 복호화 키는 relay에 보내지 않는다.

v3.0에서는 수신자 기기에 암호화한 묶음 키와 발신 증명을 지원하는 검증된 방식을 선택한다. payload 개념은 재사용하되 암호화 외피는 v2로 바뀔 수 있다. v1 호환 읽기는 유지하고, v1 공유 코드를 그대로 서버에 올리는 방식으로 팀 기능을 구현하지 않는다.

## 5. 파일 적용과 로컬 데이터 보호

이 절의 프로젝트 직접 쓰기·권한·Git 검사·백업·복구 정책은 후속 데스크톱에 적용한다. 웹은 사용자가 명시적으로 다운로드한 사본을 제공하고, 프로젝트에 자동 배치하거나 다운로드한 사본의 위치·변경·복구를 관리하지 않는다. 웹에서 다운로드 완료를 프로젝트 적용 완료로 표시하지 않는다.

공유 파일은 신뢰할 수 없는 입력으로 취급한다. 경로 검증은 미리보기와 실제 쓰기 모두에서 필요하다.

- 프로젝트 안의 일반 파일만 지원한다. 디렉터리 재귀 공유, 심볼릭 링크, 특수 파일은 제외한다.
- 절대 경로, `..`, 빈 경로, 중복 경로, `.git` 내부, Windows 드라이브·UNC·대체 스트림 경로를 거부한다. 대소문자·유니코드 정규화로 충돌하는 경로도 대상 파일시스템 기준으로 거부한다.
- 대상 폴더의 부모 경로까지 링크 여부를 확인하고, 실제 쓰기도 경로 치환을 방지하는 플랫폼 수단을 사용한다. 미리보기 직후 링크가 바뀌는 경우까지 검증 대상이다.
- 미리보기 때 기억한 로컬 파일 상태와 적용 직전 상태가 다르면 중단하고 다시 비교한다. 내보내기도 읽는 도중 파일이 바뀌면 재시도를 요청한다.
- 새 파일은 현재 사용자만 읽고 쓸 수 있는 권한으로 만든다. 기존 파일 권한을 넓히지 않으며 OS별 실제 권한 검증을 출시 조건으로 둔다.
- Git으로 추적 중인 파일은 표시하고 기본 적용에서 제외한다. 추적되지 않았지만 ignore되지 않은 대상은 적용 전 로컬 ignore 처리 또는 사용자 확인이 필요하다. 공유된 `.gitignore`를 자동 수정하지 않는다.

복구 백업은 프로젝트 밖의 앱 전용 폴더에 암호화해서 저장한다. 키는 OS 보안 저장소에 두며, 저장에 실패하면 적용하지 않는다. 프로젝트별 최근 완료한 가져오기 1회를 보관하고 사용자 삭제와 복구를 제공한다. 진행 중이거나 복구가 끝나지 않은 작업의 백업·기록은 이 보관 제한 때문에 삭제하거나 새 작업으로 덮어쓰지 않는다. 복구 키를 잃으면 백업도 복구할 수 없다.

여러 파일 교체 전체가 원자적이라고 약속하지 않는다. 전체 사전 검사 → 기존 파일·새 파일 여부의 암호화 백업 → 작업 기록 → 파일별 임시 쓰기·교체 → 완료 기록 순서로 처리한다.

확정한 복구 정책:

- 적용 중 오류: 추가 적용을 중단하고 이번 작업에서 바꾼 파일을 적용 역순으로 자동 복구한다. 기존 파일은 백업으로 되돌리고, 이번 작업에서 새로 만든 파일은 삭제한다. 앱이 적용한 이후 내용이나 상태가 바뀐 파일은 자동으로 덮어쓰거나 삭제하지 않고 사용자 확인 대상으로 남긴다.
- 앱 강제 종료: 다음 실행에서 미완료 작업을 안내하고 사용자 확인 후 복구한다. 복구를 미루면 백업·기록을 유지하고 해당 프로젝트의 새 가져오기는 기존 작업을 해결한 뒤 허용한다.
- 복구 중 오류 또는 사용자 수정 감지: 복구하지 못한 경로와 이유를 표시하고 백업·기록을 유지한다. 다시 복구를 시도하거나 사용자가 해당 파일의 처리 방법을 선택할 수 있게 한다. 모든 대상이 해결되기 전에는 복구 완료로 표시하지 않는다.
- 복호화·사전 검사 실패: 아직 대상 파일을 바꾸지 않았으므로 적용하지 않았다는 결과만 표시한다.

부분 실패의 예는 첫 파일 교체 후 다음 파일에서 디스크 공간 부족, 접근 권한 변화 또는 다른 프로그램의 파일 잠금으로 쓰기·교체가 실패하는 경우다. 적용 도중 앱이 종료되어 일부 파일만 바뀐 경우도 미완료 작업으로 취급한다.

평문 영구 캐시는 만들지 않는다. 대상 폴더의 적용용 임시 파일은 제한 권한으로 만들고 정상 종료·다음 실행 때 잔여 작업을 정리한다. Git 작업 트리 안에서는 평문을 쓰기 전에 임시 경로가 추적되지 않고 일반적인 Git 추가 대상에서도 제외되는지 확인한다. 원본 파일의 ignore 설정이 임시 파일에도 적용된다고 가정하지 않는다. 임시 경로의 제외를 확보·확인하지 못하면 평문을 쓰지 않고 적용을 중단한다. 메모리·OS 스왑·백업까지 완전한 소거를 보장한다고 표현하지 않는다.

## 6. v1.0 구현 구조

웹 클라이언트부터 시작한다. 화면과 파일·암호화 처리를 분리하되 플러그인 구조, 여러 저장소 adapter나 아직 사용하지 않는 공통 UI 패키지를 미리 만들지 않는다.

2026-09-11 개발 순서 변경: 웹의 파일 선택·암호화·인증·다운로드를 먼저 구현한다. React + TypeScript + Vite로 웹 0.0.1의 일반 파일 공유와 로컬 실시간 relay를 구현했다. 상세 버전과 실행 명령은 [README](../README.md)와 각 설정 파일을 따른다. 후속 데스크톱 프레임워크는 기존에 선택한 Tauri 2를 유지하고, 파일 접근·OS 보안 저장소·적용·복구는 Rust에서 맡는다.

후속 데스크톱에서는 WebView에 노출하는 명령과 권한을 필요한 범위로 제한한다. Rust 명령에서도 입력과 대상 경로를 검증한다. OS 공유 창과 보안 저장소 연동은 데스크톱 착수 단계 D0에서 검증한다. 기술 선택 근거: [Tauri 구조](https://v2.tauri.app/concept/architecture/), [보안 모델](https://v2.tauri.app/security/).

저장소는 Git 프로젝트 하나를 유지한다. `apps/web/`을 먼저 구현하고, 2.0에서 `apps/server/`, 후속 데스크톱에서 `apps/desktop/`을 추가해 모노레포로 운영한다. 3.0의 팀 기능과 4.0의 유료 보관도 이 서버 프로젝트에서 확장한다. 빌드와 배포는 프로젝트별로 구성한다. 공통 패키지는 실제로 함께 쓸 코드가 생겼을 때 추출하고, 언어가 달라도 공유 파일 규격과 테스트 벡터는 함께 관리한다. Turborepo + pnpm workspaces로 구성하며 선택 근거는 [웹 우선 구현 설계](web-design.md)에 둔다.

```mermaid
flowchart LR
  P[사용자가 선택한 파일] --> E[브라우저: 검증·묶기·암호화]
  E --> B[공유 파일]
  E --> K[별도로 전달하는 공유 코드]
  B --> I[브라우저: 인증·검증·내용 확인]
  K --> I
  I --> D[사용자가 다운로드]
```

웹 화면이 호출하는 최소 동작은 공유 묶음 만들기, 인증 후 열기, 선택한 파일 다운로드다. 파일 형식과 키 처리는 화면에서 분리한다. 후속 데스크톱의 `applyImport`, `restoreImport`와 구체적인 Rust 명령은 데스크톱 구현 시 확정한다.

웹 첫 구현은 파일·공유 코드·선택을 현재 탭의 작업 메모리에만 둔다. 사용자가 다운로드한 사본 외에 평문 캐시를 만들지 않는다. 후속 데스크톱에서는 최근 폴더·표시 설정과 암호화한 복구 정보를 제품 정책에 따라 보관한다. 원본 설정값을 별도 데이터베이스에 복제하지 않는다.

## 7. v2.0 실시간 relay

1.0의 파일 선택·암호화·인증을 재사용하고, 두 클라이언트 사이의 전달 기능을 추가한다. 공유 방식은 `파일로 공유`와 `실시간으로 보내기`를 함께 제공한다. 파일로 공유하면 Cloudflare relay를 거치지 않고 생성한 `.envhandoff` 파일을 AirDrop·파일 첨부 등으로 전달한다. 웹에서는 파일 다운로드를 기본 제공하고 OS 공유 창 연동 여부는 브라우저별로 검증한다. 실시간 전송을 선택한 경우에만 일회성 연결 링크를 만든다.

실시간 전송에서도 먼저 암호화 묶음과 별도의 공유 코드를 준비한다. 보내는 사람이 연결 링크를 기존 개인 대화로 전달하고, 상대가 참여하면 대화 중인 상대인지 확인한 뒤 전송을 승인한다. 링크를 열었다는 이유만으로 파일을 자동 전송하지 않는다. 전체 암호문을 받은 클라이언트에서 공유 코드로 인증·복호화한 뒤 웹은 내용 확인·다운로드로, 후속 데스크톱은 비교·적용으로 이어진다. 파일 복호화 코드는 두 공유 방식 모두 별도 경로로 전달한다.

연결된 기기 표시나 링크 소지만으로 수신자의 신원을 인증하지 않는다. 앱은 특정 이메일의 사람만 수신한다는 보장을 제공하지 않으며, 송신자 승인도 이메일 인증으로 표시하지 않는다. 개인 대화로 상대를 확인하고 공유 코드를 별도로 전달하는 흐름을 안내한다.

웹 0.0.1은 Cloudflare Workers와 Durable Objects의 WebSocket 중계를 구현했다. 현재 로컬 workerd에서 검증했으며 실제 Cloudflare 배포는 아직 하지 않았다. Workers는 세션 접근을 검사하고 Durable Objects는 해당 세션의 두 연결 사이에 암호문을 전달한다. 파일 내용·암호문·복호화 키를 데이터베이스, WebSocket 상태 보존 데이터 또는 로그에 기록하지 않는다. 암호문은 전송 중 메모리·네트워크 버퍼를 거치며, 파일 저장소에 보관하지 않는다. R2와 팀 데이터용 D1은 이 단계에 도입하지 않는다.

```mermaid
flowchart LR
  S[보내는 웹 또는 후속 Tauri 앱] -->|암호문 조각| R[Workers · Durable Objects]
  R -->|실시간 전달| D[받는 웹 또는 후속 Tauri 앱]
```

이 구조에서는 데이터가 중계 서버를 거친다. 직접 P2P 연결을 위한 WebRTC·STUN·TURN은 초기 구현 범위에 포함하지 않는다. 근거: [Durable Objects WebSocket 지원](https://developers.cloudflare.com/durable-objects/best-practices/websockets/).

세션은 무작위 접근 토큰, 송신·수신 역할 구분, 송신자가 승인한 수신자 한 명, 만료와 취소를 갖는다. 전송 크기·동시 연결·요청 빈도·전송 대기량을 제한한다. 연결 토큰은 파일 복호화 코드와 독립적으로 생성하며 계정 기반 신원 확인을 대신한다고 표현하지 않는다. 연결·승인의 메시지, 재사용 방지와 제한값은 [relay 프로토콜](relay-protocol.md)에 정리했다.

양쪽 앱이 전송 중 접속해 있어야 한다. 중간 연결 종료나 서버 재시작으로 전송을 완료하지 못하면 로컬 파일을 적용하지 않고 재전송을 안내한다. 재전송은 처음부터 다시 보내는 방식으로 시작한다. 암호문 전송이 끝나도 수신자가 코드를 입력해 확인하기 전에는 `수신 확인 대기`로 표시한다. 수신 앱의 전체 암호문 인증과 수신 완료 응답을 전송 성공 조건으로 둔다. 파일 적용 완료는 수신 완료와 별도로 표시한다.

v2.0 서버는 Cloudflare 무료 플랜의 사용량 범위에서 세션 연결과 암호문 실시간 중계만 담당한다. 이메일 인증·메일 발송 서버와 파일 보관소는 추가하지 않는다. 제한 초과나 중계 장애는 정상적인 오류 경로로 처리하고 `파일로 공유`로 돌아갈 수 있게 한다. 자동으로 유료 사용량을 허용하지 않으며, 실제 동시 연결 수·전송량과 무료 한도에서의 중단 동작은 출시 전에 검증한다. 근거: [Durable Objects 무료 플랜과 제한](https://developers.cloudflare.com/durable-objects/platform/pricing/).

## 8. v3.0 팀 공유·임시 보관

2.0의 실시간 전달에 계정·팀·초대·요청과 암호문 임시 보관을 추가한다. Cloudflare 구성에서는 팀·요청 상태에 D1, 임시 파일에 R2를 사용하는 안을 검토한다. 이 단계부터 송신자의 업로드가 끝난 뒤 다른 시간에 수신할 수 있다.

도메인 관계는 `Team → Project → Environment`이고, `Membership`은 팀 역할과 접근 가능한 프로젝트·환경을 나타낸다. `Device`는 사용자의 승인된 기기와 공개키, `Request`는 환경파일 요청, `Transfer`는 특정 스냅샷의 전달 상태다. 팀 초대만으로 모든 환경의 복호화 권한을 주지 않는다.

초기 역할은 Owner와 Member로 시작하고 환경별 받기·보내기 권한을 별도로 둔다. Owner도 실제 복호화 권한을 가진 기기나 복구 수단 없이는 파일을 열 수 없다. 마지막 Owner가 나가려면 이전 절차가 필요하다.

```text
요청: pending → approved / rejected / cancelled / expired
전달: uploading → available → acknowledged / expired / revoked
```

승인은 어떤 환경의 어떤 수신자에게 보낼지 결정한다. 실제 파일을 가진 기기가 암호화·업로드해야 `available`이 된다. 요청 승인과 업로드 완료를 같은 상태로 처리하지 않는다. 요청 자체의 만료는 제안 7일, 업로드 완료된 전달의 보관 만료는 24시간이다.

서버는 인증, 요청마다 권한 검사, 암호문 저장과 전달 상태를 담당한다. 평문과 복호화 키는 받지 않는다. 팀 관계, 계정, 접근 시각, 파일 크기 등 메타데이터는 서버에 보일 수 있음을 명시한다.

기기 등록과 공개키 신뢰가 v3.0의 핵심 선행 작업이다. 이메일 로그인만으로 복호화 키를 발급하거나 서버가 바꾼 공개키를 조용히 신뢰하지 않는다. 기존 승인 기기의 확인 또는 별도 신뢰 경로로 첫 기기를 연결하고, 키 변경을 알린다. 발신 기기와 프로젝트·환경·수신자·스냅샷의 결합을 암호학적으로 검증해야 한다. 사용할 프로토콜과 복구 설계는 v3.0 구현 전에 별도 검토한다.

동시 편집은 병합하지 않는다. 같은 요청의 중복 승인·업로드는 멱등 처리하고, 받는 쪽은 v1.0과 동일하게 로컬 변경을 비교한다. 권한 회수는 신규 승인·다운로드·향후 키 배포를 차단한다. 이미 전달된 파일이나 키를 회수한다고 표시하지 않는다.

## 9. v4.0 유료 클라우드 보관과 보안 운영

유료 가치는 파일 용량보다 지속 보관, 이전 버전 복원, 보유자의 재전송 없이 권한자가 게시된 파일을 받는 데 둔다. 팀 기본 요금과 포함 인원·보관량 형태를 가설로 두며 가격은 팀 파일럿 후 정한다. 보안을 낮춘 무료 등급은 만들지 않는다.

클라우드 버전은 불변 스냅샷으로 저장한다. 게시자가 본 이전 버전과 서버 최신 버전이 다르면 게시를 중단하고 선택을 요청한다. 복원은 과거 버전을 삭제·변경하지 않고 새 버전으로 게시한다. 감사 기록은 업로드·다운로드·권한 변경 같은 앱에서 관찰한 동작을 기록하며 실제 비밀값 사용까지 추적한다고 약속하지 않는다.

유료 출시 전에 확정할 항목:

- 신규 기기, 모든 기기 분실, Owner 부재에서의 팀 복구. 팀이 보관하는 복구 키를 제안하되 분실·오용·권한 범위를 검토한다.
- 탈퇴·퇴사 시 향후 버전 키 갱신과 이미 유출된 서비스 자격증명의 별도 교체 절차.
- 파일·계정 삭제 시 활성 저장소, 복제본, 백업 각각의 삭제 기한과 사용자 안내.
- 결제 실패 때 비밀파일을 즉시 삭제하지 않는 유예·내보내기 정책.
- 클라우드 저장·접근 권한·기기 복구까지 포함한 외부 보안 검토.

보호하려는 것은 공유 채널이나 저장소에서 파일만 유출되는 상황, 암호문 변조, 악성 경로 입력, 실수로 인한 로컬 덮어쓰기다. 감염된 기기, 이미 받은 팀원의 재공유, 파일과 코드가 함께 유출된 상황까지 막지는 못한다. 서버가 암호문만 갖는다는 사실만으로 서비스 전체가 안전해지는 것은 아니다.

인증된 암호화, 안전한 난수, 키와 데이터의 분리, 최소한의 비밀 보관을 기본 원칙으로 삼는다. 참고: [OWASP Cryptographic Storage](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html). 접근 최소화, 키 수명과 회수·감사 절차는 [OWASP Secrets Management](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)를 기준으로 구현 검토한다. 이 문서는 보안 인증이나 검토 완료를 의미하지 않는다.

## 10. 구현 순서와 검증

웹 첫 출시부터 공식 HTTPS 배포 경로, 배포 의존성 검증, 보안 수정본 전달 방법, 취약점 신고 경로와 침해 대응 절차를 둔다. 후속 데스크톱은 배포물 서명과 공식 다운로드 경로도 출시 조건으로 둔다. 데스크톱 자동 업데이트는 필수가 아니며, 도입하면 업데이트 파일의 출처·무결성을 검증한다.

| 순서 | 작업 | 완료 증거 |
|---|---|---|
| M0 | 웹 최소 화면·파일 선택 연결, 모노레포 기본 설정, 암호 왕복과 포맷 v1 고정 | 가짜 파일의 선택·취소·제한 검사, 암호화→복호화, 경로·파일 형식 테스트 벡터 |
| M1 | 선택한 파일 내보내기·읽기 | `.env`와 JSON의 바이트 단위 왕복, 잘못된 키·변조·잘림 거부 |
| M2 | 웹의 인증 후 내용 확인·개별 파일 다운로드 | 파일 내용을 실행·HTML로 해석하지 않음, 잘못된 코드·경로·형식 거부, 원본 바이트 보존, 다운로드와 프로젝트 적용 구분 |
| M3 | 웹 화면 연결과 브라우저 검증 | 실제 두 기기로 공유 파일 다운로드→개인 전달→파일·코드로 열기→원본 파일 다운로드 |
| M4 | 웹 일반 공유 내부 검증 | 두 기기의 파일·코드 전달, 인증·다운로드 흐름과 파일 보호 조건 통과 |
| M5 | 2.0 실시간 relay와 화면 연결 | 송신자 승인 전 미전송, 두 기기의 전체 수신·암호문 인증 응답, 만료·중단·새 연결 재전송, 무료 한도·중계 장애 시 파일 공유 전환 검증 |
| M6 | 개발팀 파일럿·웹 첫 배포 준비 | 웹 1.0과 2.0 사용성, 지원 브라우저, 파일 보호와 중계 제한·배포 조건 검증 후 첫 배포 |
| D0 이후 | 후속 Tauri 앱의 폴더 선택·Git 검사·OS 공유·키 보관·적용·복구 | macOS·Windows에서 파일 권한·임시 파일 Git 제외·부분 실패·재실행 복구와 웹 파일 호환성 검증 |

안전 검증은 실제 비밀값 대신 가짜 파일로 실행 가능한 통합 검사에 모은다. 웹은 지원 브라우저에서 암호 왕복·잘못된 코드·변조·제한 초과·중단·다운로드를 확인한다. 후속 데스크톱에서는 임시 디렉터리를 사용해 OS별 경로·권한 검사와 쓰기 실패·앱 종료 시 원본 보존·복구를 추가 검증한다. 현재는 웹 0.0.1의 파일 처리·실시간 전달과 자동 테스트를 구현했다. `pnpm check`가 lint·타입 검사·파일 검증·실제 로컬 workerd 통합 테스트·빌드를 실행한다. Chromium의 일반 공유와 두 탭 relay에서 원본 바이트 왕복을 확인했으며, 두 기기·지원 브라우저·Cloudflare 배포 검증은 남아 있다.

파일럿 목표는 2~3개 개발팀, 각 팀에서 보내는 사람·받는 사람 모두 사용이다. 웹 진입 후 첫 공유·파일 다운로드 3분 이내를 가설로 삼고, 개발 설정을 받는 데 필요했던 별도 메시지 수와 직접 배치하는 수고를 관찰한다. 실제 키·파일 내용은 수집하지 않는다. relay는 일반 공유의 핵심 동작을 완성한 뒤 구현하며 첫 배포에 포함한다.

2.0에서는 두 기기의 전송 성공 외에 승인 전 미전송, 추가 수신자·무단 세션 참여 거부, 만료·취소, 잘못된 코드·변조, 전송 크기·대기량 초과, 연결 종료·서버 재시작 시 미적용과 재전송을 검증한다. 무료 한도나 중계 장애로 전송할 수 없어도 파일 공유를 사용할 수 있는지, 두 공유 방식 모두 계정·이메일 인증을 요구하지 않는지 확인한다. 파일 내용·암호문·복호화 키가 서버 저장소나 로그에 남지 않는지도 확인한다. 3.0에서는 팀 권한과 임시 보관의 비동기 수신을, 4.0에서는 지속 보관·버전 복원·과금과 복구를 검증한다.

## 11. 미결정 사항

1. 웹 지원 브라우저의 실제 파일 처리 동작: Chromium 로컬 왕복을 확인했다. 두 기기·Safari·Firefox·모바일 기기 검증은 배포 전에 수행한다. 개발 도구는 React + TypeScript + Vite, Turborepo + pnpm으로 구성했다. 후속 데스크톱의 지원 OS·OS 공유·보안 저장소 구현은 D0에서 확정하며 프레임워크는 Tauri 2를 유지한다.
2. Web Crypto API를 이용한 암호 왕복과 v1 바이트 규격: 0.0.1 구현과 공개 테스트 벡터로 고정했다. Rust 암호 라이브러리는 후속 데스크톱에서 같은 규격으로 검증한다.
3. 크기 제한, 백업 1회, 3.0의 임시 보관 24시간·요청 7일: 초안의 제안값. 파일럿으로 조정.
4. 실시간 relay의 연결·승인 메시지 규격, 토큰 재사용 방지와 제한값: 0.0.1에서 구현하고 로컬 workerd로 검증했다. 개인 대화로 상대 확인 후 송신자가 승인하는 흐름과 이메일 인증 제외는 합의했다. 무료 플랜 내 동작과 중단·재전송 처리를 포함해 검증한다.
5. 팀 기기 승인·발신 인증·복구 프로토콜: v3.0 착수 조건. 현재 구현 범위에는 포함하지 않는다.
