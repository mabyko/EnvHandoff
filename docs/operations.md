# Pro API 운영과 재해 복원

이 문서는 현재 구현의 운영 절차다. 호스팅 업체·운영 접속 정보·실제 HTTPS 배포는 아직 정하지 않았으며, 로컬 검사 통과를 운영 구성 검증으로 취급하지 않는다. QA 결과는 [QA 기록](qa.md)에 둔다.

## 배포 전 조건

- API와 웹은 HTTPS의 같은 site 하위 도메인으로 배포하고 정확한 `WEB_ORIGIN`, `API_ORIGIN`을 설정한다. 개발용 localhost 예외를 운영에 사용하지 않는다.
- 운영 주소는 `WEB_ORIGIN=https://envhandoff.mabyko.com`, `API_ORIGIN=https://api.envhandoff.mabyko.com`이다. 웹 빌드의 `VITE_PRO_API_ORIGIN`도 API 주소와 맞추고 GitHub OAuth callback은 `https://api.envhandoff.mabyko.com/auth/github/callback`으로 등록한다. DNS·인증서·OAuth 운영 등록은 배포 시 수행하며 코드 기본값 변경만으로 적용되지 않는다.
- API 호스트에 맞는 HTTPS 인증서를 발급한다. `mabyko.com`을 Cloudflare full DNS zone으로 운영하면서 프록시를 켠다면 기본 Universal SSL은 이 깊이의 하위 도메인을 덮지 않으므로 별도 edge 인증서 구성이 필요하다. DNS only로 연결한다면 Openship/서버가 해당 호스트의 공개적으로 신뢰되는 인증서를 제공해야 한다. [Cloudflare 인증서 범위](https://developers.cloudflare.com/ssl/edge-certificates/universal-ssl/limitations/), [Openship 사용자 도메인](https://openship.io/docs/guides/custom-domains)
- `DATABASE_URL`은 전용 PostgreSQL 계정과 검증된 TLS 설정을 사용한다. 개발·테스트 DB를 운영에 재사용하지 않는다.
- `FILE_STORAGE_PATH`는 API만 접근하는 영속 경로다. 웹 정적 파일·CDN·공개 버킷과 분리하고 객체 백업·버전 보관을 끈다. 서버 재시작 때 경로가 교체되거나 초기화되지 않아야 한다.
- API 인스턴스가 여러 개면 같은 객체 저장소를 읽고 삭제할 수 있어야 한다. 현재 접속 주소별 제한은 단일 프로세스용이며, 여러 인스턴스에는 공유 edge 제한이 필요하다.
- 프록시는 정확한 Host를 API에 전달해야 한다. 현재 API는 임의의 forwarded IP 헤더를 신뢰하지 않는다. 요청/응답 본문, 쿠키, 공유 토큰 헤더, URL fragment와 공유 코드가 로그·분석 도구에 수집되지 않도록 설정한다.
- `TOTP_ENCRYPTION_KEY`는 DB 밖에서 보호하고 재배포 때 유지한다. 운영 키나 OAuth secret을 웹의 `VITE_*` 설정에 넣지 않는다.
- `DELETION_LEDGER_PATH`는 DB 스냅샷과 독립된 영속 삭제대장 전용 디렉터리다. `FILE_STORAGE_PATH`와 공유하지 않고 DB 복원 때 과거 사본으로 되돌리지 않는다. 최초 설치에서만 `pnpm --filter @envhandoff/api deletion-ledger --init`으로 생성한다. 기존 디렉터리는 덮어쓰지 않으며 분실·손상·다른 대장 연결은 API 시작/요청을 차단한다. 개발 기본 경로도 최초 명시 초기화가 필요하다.
- 베타 한도는 [limits.ts](../apps/api/src/limits.ts)에 모아 버전 관리한다. 초기 값 조정은 해당 설정과 화면의 한도 안내를 함께 갱신하고 재배포·회귀 검사를 거친다. 파일 형식·암호 규격·보안 유효 시간은 이 설정으로 바꾸지 않는다.

## 삭제와 관찰

API가 매분 만료·회수·실패 객체를 정리한다. 객체 삭제가 성공해야 저장 용량을 반환한다. 정상 API 재시작은 원래 기한 내 전달을 유지한다.

같은 분 단위 작업에서 정리 후에도 남은 지연을 감지하고 `event: deletion_delayed` JSON 경보를 stderr로 출력한다. 정리 자체가 실패해도 진단은 시도한다. 요약은 팀 전달/외부 공유별 건수와 최장 경과 시간뿐이며 파일·계정 ID, 경로, 키·토큰을 포함하지 않는다. 진행 중 업로드가 1시간 이상 종료되지 않았거나, 종료된 객체가 24시간 이상 삭제되지 않았으면 지연으로 본다. 미래의 writer lease가 있어도 지연 집계에서 빼지 않는다.

API가 중지돼 있어도 별도 감시에서 다음 읽기 전용 명령을 실행할 수 있다. 마이그레이션된 `DATABASE_URL`만 필요하며 DB·객체·삭제대장은 변경하지 않는다.

```sh
pnpm --filter @envhandoff/api deletion-health
```

종료 코드는 정상 `0`, 지연 `1`, 점검 실패 `2`다. 외부 감시 도구에는 이 종료 코드와 JSON 요약을 연결한다. 집계 진단 실행 기록은 해당 운영 감시 로그에 보관한다. 실제 감시 일정·알림 수신처 연결과 API 중단 감시는 아직 운영 설정 작업이며, 이번 구현에서 외부 알림을 발송하지 않았다.

운영 감시에서는 다음을 확인한다.

1. API 정리 오류와 `object_delete_failed` 사건이 반복되지 않는지 확인한다.
2. `deletion_delayed`와 `deletion-health` 지연/실패 종료를 감시한다. 삭제 미완료를 완료로 표시하지 않는다.
3. PostgreSQL과 객체 디스크의 여유 용량, API 응답 실패·제한 응답을 확인한다. 한도를 자동으로 올리거나 유료 확장을 허용하지 않는다.
4. API가 중지되거나 저장소에 접근하지 못해도 24시간 삭제 목표를 지킬 운영 대응 경로를 마련한다. 코드의 재시도만으로 운영 삭제 기한이 보장되지는 않는다.

## 백업

암호문 파일과 감싼 키가 포함된 객체는 별도로 백업하지 않는다. 메타데이터 백업은 암호화해 최대 7일 보관하며 `external_shares.token_hash`와 토큰 관련 일회성·재시도 자료를 제외한다. `share_operations`, `transfer_challenges`는 복구 자료로 사용하지 않는다. 복호화 코드와 파일 키는 원래 서버에 전달하지 않는다.

실제 백업 도구의 열·테이블 제외, 복제본과 스냅샷의 삭제 기한, 복원 절차는 운영 제공자를 정한 뒤 검증해야 한다. 일반 DB 전체 덤프를 그대로 정책에 맞는 백업이라고 간주하지 않는다.

## 과거 백업에서 복원할 때

오래된 DB에는 회수 전 권한·토큰·전달 상태가 남아 있을 수 있다. 정상 재시작과 구분해, **API를 중지하고 외부 요청을 차단한 상태**에서 복원된 전달을 모두 닫는다. 이 명령은 현재 권한·기기 관계 자체를 복구하거나 실제 계정 상태를 검증하지 않는다. 재전송을 허용하기 전에 운영자가 현재 소속·권한·기기 상태도 확인해야 한다.

1. 운영 트래픽과 모든 API 프로세스를 중지한다. 오래된 업로드 프로세스가 살아 있어서는 안 된다.
2. 복원 DB에 필요한 마이그레이션을 적용한다. 다음 명령의 `DATABASE_URL`이 복원 대상 DB인지 확인한다.
3. 독립 삭제대장을 연결한 뒤 저장소 루트에서 차단 대상 수를 확인한다. 기본 동작도 영구 삭제 기록을 먼저 적용하고 미리보기 열람 감사를 남긴다. 나머지 활성 전달의 일괄 폐기는 `--apply`에서만 수행한다.

   ```sh
   pnpm --filter @envhandoff/api restore-safe
   ```

4. 복원 대상이 맞으면 차단을 적용한다.

   ```sh
   pnpm --filter @envhandoff/api restore-safe --apply
   ```

5. 종료 코드 0과 `applied: true`, `auditRecorded: true`를 확인한다. 실패하면 API를 중지한 채 원인을 해결한다. 미리보기·적용·재실행은 각각 열람 감사를 남기며, 다시 실행해도 종료된 전달을 열거나 과거 ACK를 지우지 않는다.
6. API가 중지된 상태에서 기존 전용 객체 볼륨의 암호문을 폐기하고 새 빈 비공개 볼륨을 준비한다. 백업 이후 생성된 객체는 복원 DB에 행이 없어 정리 작업이 찾지 못할 수 있다. 모든 이전 전달을 폐기했으므로 이전 객체 볼륨을 다시 연결하거나 복구용 사본으로 보관하지 않는다. 다른 서비스와 공유하는 경로를 삭제하지 말고, 운영자가 정확한 전용 볼륨을 확인해 처리한다.
7. 현재 권한·기기 상태를 점검한 뒤 API를 시작한다. 시작 시 정리가 차단한 객체의 부재를 확인하고 삭제 완료를 기록하며, 실제 삭제 확인 전에는 용량이 계속 예약된다. 삭제 실패를 해결하고 기존 공유는 재전송하도록 안내한다.

명령은 하나의 DB 거래에서 미이행 요청·진행 중 업로드를 취소하고, 팀원 전달·외부 공유를 회수하며, 모든 외부 토큰 해시·링크 재시도 기록·전달 도전을 제거한다. 종료 시각과 기존 ACK는 보존하며 물리 삭제를 완료한 것으로 표시하지 않는다. 소급 회수한 로컬 사본을 삭제하거나 노출된 서비스 자격 증명을 폐기하는 명령은 아니다.

실제 재해 복원 훈련과 운영 제공자의 백업 설정은 별도 출시 조건이다. 이 명령을 일반 배포나 정상 재시작에 자동 실행하지 않는다.

## 정상 베타 종료

최소 7일 전 기존 연락 경로로 종료를 공지한다. 신규 접수 종료 시 `PRO_ACCEPT_NEW_TRANSFERS=false`로 재시작한다(정확한 `true`/`false`만 허용). 새 요청·예약·업로드를 거부하고 기존 예약 결과 조회·다운로드·ACK·회수와 원래 기한은 유지한다. 이 설정은 계정·조직 중지나 기존 전달 일괄 회수와 별개다.

## 긴급 계정 중지

`DATABASE_URL`과 독립 `DELETION_LEDGER_PATH`를 확인하고 다음 명령으로 대상을 먼저 조회한다. 두 ID가 같은 계정에 속해야 하며 로그인 이름으로 대상을 추측하지 않는다.

```sh
pnpm --filter @envhandoff/api disable-account <내부-사용자-UUID> <GitHub-숫자-ID>
```

대상을 확인한 같은 명령에 `--apply`를 추가하면 계정 비활성화·전체 세션 및 관련 OAuth 거래 폐기·발급/수신 대기 초대 취소·연관 요청/전달 차단을 하나의 거래로 처리한다. 기존 `AuthApi.disableUser`도 같은 처리 함수를 사용한다. 기본 조회는 중지하지 않고 열람 감사를 남기며, 마이그레이션과 영구 삭제대장의 우선 적용은 수행한다. 성공 결과의 `applied`와 `auditRecorded`를 확인한다. 실패한 실행은 완료로 간주하지 말고 다시 조회한다.

긴급 상황에서는 마지막 Owner도 중지할 수 있다. 대체 Owner가 필요하면 아래 관리 역할 복구 절차를 따른다. 계정 중지는 계정 삭제·기기 키 초기화가 아니며 재실행해도 이전 회수 시각이나 권한을 되살리지 않는다. 자동 연락 발송·중지 해제·공개 운영자 HTTP API는 제공하지 않는다.

## 다운로드 거부 기록

팀 전달의 다운로드/다운로드 도전과 외부 공유 다운로드가 거부되면 실제 확정 객체에 대해 `download_denied` 또는 `share_download_denied`를 남긴다. 권한·기기 증명·토큰·만료·한도 거부를 포함하며 실패한 전달 거래가 롤백돼도 별도 감사 거래로 저장한다. 기존의 불투명한 오류 응답은 유지한다.

기록은 내부 조직/대상 ID, 인증된 경우의 요청자 ID, 사건·시각만 포함한다. 공격성 반복 기록을 제한하기 위해 대상·사건 종류당 1분에 한 건만 남기는 표본 기록이다. 전체 거부 횟수 집계로 해석하지 않는다. 없는 대상, 비회원 미리보기·ACK, 전달 처리 진입 전의 HTTP 인증/CSRF·접속 주소 제한 거부는 이 대상별 다운로드 기록 범위에 포함하지 않는다. 감사 저장 실패도 원래 다운로드를 허용하지 않으며 별도 오류 로그를 남긴다.

## 관리 역할 복구

온보딩 연락 검증 증빙은 별도 운영 기록에 보관하고 제품에는 UUID 참조만 등록한다. 연락처·대화 내용·비밀값을 CLI 인수에 넣지 않는다.

```sh
pnpm --filter @envhandoff/api management-recovery --help
```

`register-contact --org <UUID> --contact-ref <UUID> --case-ref <UUID> --attest-contact-verified`로 최초 연락 경로를 등록한다. `recover --org <UUID> --contact-ref <등록 UUID> --case-ref <새 UUID> --login <GitHub 로그인> --github-id <숫자 ID> --owners <기존 Owner 숫자 ID 쉼표 목록 또는 none> --attest-contact-verified --attest-all-owners-lost`로 복구 대상을 조회한다. 두 명령 모두 기본은 미리보기이며 확인한 같은 명령에 `--apply`를 추가해야 적용한다.

미리보기도 마이그레이션·영구 삭제 적용과 열람 감사는 수행한다. 연락 등록·역할·세션·초대는 바꾸지 않는다. 연락 참조는 최초 등록 후 임의 교체할 수 없다. 복구 대상은 먼저 로그인한 활성 계정이어야 하며 신규 조직 멤버라면 20명 한도와 팀/파일 권한 기본 거부를 유지한다. 적용은 기존 Owner를 Member로 바꾸고 대상에 Owner를 부여하며, 기존 Owner와 대상의 모든 세션·관련 OAuth 거래, 해당 조직의 미완료 초대를 폐기한다. 기기 키·신뢰와 파일 권한은 복구하지 않는다.

실제 연락 검증은 운영자가 수행하며 CLI는 자동 연락을 보내지 않는다. 직접 DB·백업에 접근하는 운영자의 열람 감사는 인프라에서 별도로 수집해야 한다.
